The chargeback platform, end to end

How a multi-country card dispute platform fits together: cases, evidence, deadlines, network submissions and the money it asks the ledger to move. Written to be understood first, then practised backwards through the seven interview stages.

Compiled from the Nubank Lead System Design Study Guide (Mock B: card disputes and chargebacks), plus what 2026 candidates report about the round itself (see section 2). Companion to the ledger notes; the ledger is the system this platform sends money commands to. Updated 6 September 2026.

1. The end result

Prompt: design a multi-country card dispute platform with evidence, deadlines, network submission, provisional credits and audited outcomes.

The chargeback platform is a case-management system. It owns the story of one dispute (what happened, who did it, when, and under which rule) and it asks other systems to do things: the card network to carry the dispute, object storage to hold documents, the ledger to move money. It is not the ledger and it is not the network.

The ledger's job was to be fast and never wrong about money. This system is slow (a case lives for weeks), but it must never lose a deadline, never forget a side effect it promised, never lose the audit trail, and never let "the case is won" be confused with "the customer has been paid". Here is the complete system you would arrive at by the end of the interview:

The six nouns

DisputeCaseThe current summary of one dispute: state, disputed amount, country, network, reason code, assigned owner, and the policy version that evaluated it. This is the snapshot you read.
CaseEventOne immutable fact from the case's history: OPENED, EVIDENCE_ADDED, ELIGIBLE, SUBMITTED, NETWORK_ACKED, WON. Every event records actor, reason and time. The snapshot can be rebuilt from the events.
DeadlineA due time saved as a row in the database with a type (respond to network, chase customer for evidence) and a status (open, claimed, done, breached). Not an in-memory timer.
EvidenceItemMetadata for one document version: object reference in encrypted storage, checksum, media type, scan status, uploader, retention class. The bytes live in object storage, never in the case row.
NetworkSubmissionThe stable external reference we sent to the card network for this case, and whether the network acknowledged it. Reused on every retry so a resubmission can never open a second dispute.
FinancialActionOne money step the case intends: provisional credit, reversal, adjustment. Each carries its own ledger idempotency key, like CB-812:PROVISIONAL_CREDIT:v1. The intent is committed here; the posting happens in the ledger.

The case is the aggregate root. Everything changes through commands, never by editing a status column.

One dispute, start to finish

  1. Ana taps "I don't recognize this purchase" on a R$300 card transaction. The app sends an OpenDispute command with an idempotency key. The platform checks she owns the card, that no open case already exists for this transaction and reason family, and that the transaction is within the dispute window under policy version 12.
  2. In one commit it writes: a CaseEvent OPENED, the DisputeCase snapshot (state OPENED, version 1, policy v12), a Deadline row (customer must supply evidence within 10 days), the idempotency record, and outbox rows (notify Ana; evaluate provisional credit). It returns "case CB-812 opened".
  3. Policy says provisional credit applies. A worker issues the RequestProvisionalCredit command; the commit records a FinancialAction with key CB-812:PROVISIONAL_CREDIT:v1 and an outbox row. After commit, a worker sends that command to the ledger. The ledger posts R$300 to Ana's account and returns its transaction id. A new CaseEvent PROVISIONAL_CREDIT_POSTED records the observed result. Ana sees the money; the case says "under review".
  4. Ana uploads a screenshot. The bytes go to encrypted object storage via a staged upload. The commit writes an EvidenceItem in state UPLOADED. A scan worker checks checksum, format and malware, then a command moves it to EVIDENCE_READY. It is not usable evidence until then.
  5. A worker evaluates eligibility against policy v12, the case moves to ELIGIBLE, and a Submit command creates a NetworkSubmission with reference NB-CB-812-1. After commit, the network adapter sends it. The network acknowledges; a new event records it and the old deadline is completed while a new one is created from the network's response window (merchant has 30 days to represent).
  6. Weeks later the network returns the award. If Ana wins in full, the case is WON and the FinancialAction is finalized. If she loses, a REVERSE_PROVISIONAL:v1 action asks the ledger for a linked reversal. If she wins R$200 of R$300, one FINAL_ADJUSTMENT:v2 for −R$100. The case closes only when the workflow decision and the financial settlement are both confirmed and the three truths agree: network award, case decision, ledger posting.

Two ways to talk to the network, and why the platform doesn't care which

The walkthrough above assumes a real-time adapter: send the submission, get an acknowledgement back. That is one shape. Candidates in 2026 also report a prompt where the exchange with the network is a batch file: the platform writes disputes into a CSV, uploads it by FTP to Mastercard four times a day, and later receives a file back with the network's answers. Section 10 covers that variant in full.

What matters here is that nothing in the case model changes. A NetworkSubmission still has a stable external reference and an acknowledged flag. The only difference is what "sending" means: one HTTP call, or one row in a file that goes out at 14:00. The batch shape adds two nouns, a BatchRun (one file, one upload, one status) and a ReconciliationItem (one thing we sent that the network hasn't answered yet), and moves the uncertainty from "did the call arrive?" to "did the file arrive, and which rows in it did they accept?".

Real-time:  case commit → outbox → adapter sends one submission → ack event
Batch:      case commit → outbox → row waits in a batch → file built + uploaded at 14:00
                                                       → ack file arrives later → one event per row

If the interviewer opens with the batch version, start from the same six nouns and the same atomic commit, then say "the network leg is a file, so I'll add a batch run and per-row reconciliation". That sentence tells them you see the stable core under the delivery mechanism.

The sentence that ties it together

"A case command commits workflow state and intent locally; external side effects happen after commit and are recorded as new events. Won is a decision; financially settled is a fact."

2. How the interview will most likely go

What Nubank says about the round, what 2026 candidates report, and a minute-by-minute plan for the hour.

What Nubank itself says

The hiring page describes the round in one line: whiteboard-style, you design a system from scratch, with a focus on scalable systems and trade-offs, and they care more about how you think and justify decisions than about landing on a single "correct" architecture. Read that literally. There is no answer key. There is a reasoning style they are listening for, and the seven stages in this guide are built to make that style visible.

What candidates report

Length45 to 60 minutes, so about 40 minutes of actual design after introductions and your own questions. Enough for one system done properly. Not enough for a tour of everything you know.
PeopleOne or two engineers, often from a platform or core banking team. One 2026 candidate had two interviewers of whom one seemed disengaged; don't read the room too hard, keep talking to the one who is.
ToolA shared whiteboard such as Miro or Excalidraw. No code. Practise drawing the section 1 diagram from memory in under three minutes.
PromptChargebacks is the single most-reported 2026 prompt: three separate candidates name it. One describes a "chargeback ingest system" that stores transactions in CSV and sends them by FTP to Mastercard four times daily. The other recurring prompts are a double-entry ledger, a real-time fraud or risk pipeline, and a credit limit or card authorisation service.
RhythmRoughly every ten minutes the interviewer adds a constraint that breaks the current design: volume goes up tenfold, a downstream service becomes unavailable, a regulator asks you to reproduce a balance or a case as it stood three months ago. A Lead candidate who did not pass reported many questions about scalability and how to improve performance.

What they are grading

Four things, in rough priority order:

  1. Immutable facts, derived state. Do you append events and rebuild a snapshot, or do you overwrite a status column? This is the most Nubank-specific signal: their whole stack (Clojure, Datomic) is built on it. "Reproduce the case as it stood on 3 June" must be a one-sentence answer: replay the events up to that date.
  2. Idempotency, raised by you. The moment a command, an API or a file crosses a boundary, you say what its stable identity is before they ask. Waiting to be asked is a negative signal in every report.
  3. A named consistency line. Which parts must be strongly consistent (case transitions, deadlines, financial intent) and which may lag (search, notifications, analytics). "Strong everywhere" is an unexamined answer, not a safe one.
  4. Partial failure. The timeout that means unknown, the message delivered twice, the partner that stops responding mid-transaction, the file that half-arrives.

The listed mistakes are the mirror image: designing a generic web system (rate limiters, CDNs, cache tiers), mutating balances or statuses in place, claiming strong consistency everywhere, and having no story for duplicate messages from the partner network.

When they push on scalability and performance

A Lead candidate who did not pass the architecture round in late 2025 reported that the questions were mostly about scalability and how to improve performance. This is the most common shape of the ten-minute interruption, and for a Lead role it is where the bar sits: not "can you add machines" but "do you know which part of your own design does not get faster by adding machines, and what you'd do about it".

The five-step answer, every time. Say the steps out loud; the structure is half the score.

  1. Ask what grew. Cases per day, files per day, documents per case, operators, countries? Each stresses a different part. "Tenfold" with no noun is a trap; name the noun yourself if they don't.
  2. Name the bottleneck, with a number you'd measure. Queue age, p99 of the command path, oldest unprocessed deadline, outbox lag, database write throughput, index lag. A bottleneck you can't measure is a guess.
  3. Scale what scales. Anything idempotent and stateless goes horizontal: workers, adapters, parsers, projections.
  4. Say what doesn't, and why. The claim step is one conditional update; the case store is a single write authority per case; Operations is people. Naming these honestly is the Lead signal.
  5. Protect the invariants while you scale. Whatever you change, transitions stay validated, deadlines stay durable, keys stay stable, history stays append-only. If a "performance improvement" needs one of those to bend, it isn't one.

"How would you improve performance?" is a different question from "scale", and it usually means latency on the customer-facing path. The answer is what is on the critical path and what you can take off it. On the command path only three things must be synchronous: permission, the idempotency and version check, and the atomic commit. Policy evaluation can be precomputed. Notifications, search, the ledger call and the network call are already after commit. So the customer-visible latency is one indexed read and one commit; if p99 is bad, the answer is a hot partition, a lock held too long, or a synchronous call that shouldn't be there, in that order. Never "add a cache in front of the case store": a cached case is exactly what lets two operators decide the same case twice.

Avoid saying

"Add more instances" without naming what they'd be instances of. "Cache the balance / cache the case." "Move to NoSQL" as if the store were the problem. "Shard everything" without a key. Each of these tells the interviewer you're answering a different, generic question.

Interview sentence

"Everything idempotent scales horizontally; the case store partitions by case id because no transaction spans two cases; the one thing that doesn't scale by adding machines is manual review, so the honest performance lever is deciding what to automate, and I'd decide that from shadow results, not from average handle time."

Their vocabulary, used lightly

You don't need Clojure. You should be able to say three things in their language. "Your Datomic transaction function is where my check-and-write becomes one atomic operation." "Kafka carries the outbox events between services; every consumer dedupes on a correlation id, which is how you already do it." "The case is an append-only history plus a materialised snapshot, which is the same shape as an immutable database with a current view." Say each once, at the moment it fits, and move on.

Caveat

Everything above is candidate-reported. Nubank publishes no question bank, sample sizes are small, and none of the reports come from the Buenos Aires team specifically; interviewers for Argentina may be drawn from Brazil, Mexico or the US. Prepare chargebacks first, the ledger second, and be able to pivot the same seven stages to an authoriser or a credit-limit service.

3. The boundary

Stage 1: what am I actually building?

Issuer, acquirer and network

Three parties. The issuer is the cardholder's bank (Nubank, for Ana). The acquirer is the merchant's bank. The card network (Visa, Mastercard, Elo) carries the rules, the messages and the deadlines between them. Ana disputes a purchase with her issuer; the issuer submits the dispute through the network; the acquirer and merchant may respond with their own evidence ("representment"); the network arbitrates.

Default to the issuer workflow, because the customer opens the dispute and that's Nubank's seat. Keep the network and acquirer behind adapters. Don't quietly build both sides in one vague workflow: they have different actors, evidence, rules and owners.

What you must establish before drawing

  • Issuer side, acquirer side, or both.
  • Countries, networks, reason codes. Each changes deadlines, evidence requirements and message formats.
  • Who owns policy and legal deadlines. Legal, compliance, network specialists and Operations own the meaning; engineering implements versioned, testable rules and records which version was applied.
  • When provisional credit is owed. Not every opened dispute credits the customer; it's a separate policy decision by product, jurisdiction and risk.
  • What already exists: card transaction store, identity, the ledger, object storage, notifications, network gateways. Integrate, don't rebuild.
  • Volume, document sizes, retention, and how much of the work is manual operations.

What is synchronous

Case acceptance, validation errors and the current customer-visible state return synchronously. Network submission, evidence processing and financial actions are asynchronous with explicit Processing states and SLAs. "Synchronous" means durable acceptance, not completion of every external step. Never block Ana's request on the card network.

What changes between countries and networks, and what doesn't

Changes: reason codes, deadlines, evidence requirements, message formats, provisional-credit rules, representment stages, currencies, retention. Stable: versioned case transitions, durable obligations, audit, idempotent side effects, reconciliation. Put the variation in policies and adapters; never fork the platform per country.

Say it in 30–60 seconds

A dispute platform is a case-management system that coordinates four things: customer intake, evidence, deadlines, and messages to the card network, plus money actions it asks the ledger to do. It is not the ledger and not the network. I clarify: are we the issuer, the acquirer, or both? Which countries and networks? Who owns the legal rules and deadlines? And does opening a case ever move money by itself, or is provisional credit a separate policy decision?

Avoid saying

Anything that makes case OPENED equivalent to CREDITED. Anything that hard-codes a legal deadline without a named business owner. Redrawing identity, money or card-network internals.

Interview sentence

"I'll separate customer intake, dispute workflow, network interaction and financial posting before selecting components."

4. The invariants

Stage 2: the rules that must hold under retries, concurrency, crashes and weeks of elapsed time.

  1. Only valid transitions occur. A case follows allowed steps under a versioned policy. It cannot jump from OPENED to CLOSED unless a rule permits it, and an operator override needs the right role plus recorded actor, reason, evidence and approval.
  2. Every action records actor, reason and time. Events are the audit trail. There is no such thing as an anonymous status change.
  3. Deadlines are deterministic and cannot disappear. A due date is a durable business obligation stored transactionally, not an in-memory timer. If every worker is down at noon, the row still exists and a sweeper finds it later.
  4. Financial actions are separately idempotent. Each credit, reversal or adjustment has its own stable key, so a retry never credits twice and one case can legitimately have several money steps.
  5. Network submissions reuse stable external references. The same reference on every retry; a fresh reference could open a duplicate dispute at the network.
  6. Evidence is versioned, access-controlled and retained by policy. A replaced document is a new version linked to the old one; the old object is never overwritten; the case records which version was sent externally.
  7. The case records which policy version evaluated it. Otherwise a rule deployment silently changes the meaning of old decisions.

The follow-ups

  • How do you guarantee a deadline is never silently missed? You can't guarantee workers never fail, so you guarantee the obligation stays durable and observable: store it transactionally, schedule a timer, run an independent sweeper, alert before and after breach. Use leases or conditional claims so retries are safe.
  • Can an operator move a case from opened to won? Only if a versioned policy explicitly permits that command and the operator has the role. Otherwise the state machine rejects it. High-value overrides need four-eyes approval. Never a direct status-column update.
  • How do you prevent duplicate disputes for the same purchase? Request idempotency alone isn't enough: two different taps have two different keys. Add a business uniqueness rule on transaction, claimant, reason family, disputed amount scope and case lifecycle. Return the existing case or a deterministic conflict. Don't use transaction id alone; partial disputes are legitimate.
  • Can a policy change alter an already-open case? Normally no; the case keeps the version used for each decision. A new legal rule triggers an explicit migration or re-evaluation command that records old and new outcomes. A version transition is a business event, not an invisible reread of config.
  • Which invariant matters most when the network is unavailable? Preserve durable case state, deadlines and stable submission identity. Queue the work, show the customer Reviewing or Delayed, never fabricate a network outcome, never duplicate a submission. Never mark FAILED just because a dependency timed out.

Say it in 30–60 seconds

A case only moves through allowed steps. Every action records who, why and when. A deadline is a saved row that cannot disappear if a worker dies. Each money action has its own stable key, so a retry never credits twice. Every message to the card network reuses the same external reference. Evidence is versioned, access-controlled and kept as long as policy says. Speed matters less here than in payments; audit and deadline correctness matter more.

Interview sentence

"The workflow is slower than authorization, but deadline, audit and financial correctness are strict."

5. The domain model

Stage 3: only the entities needed to enforce transitions, deadlines, audit and linked financial actions.

Event plus snapshot

Every command appends a CaseEvent and updates the DisputeCase snapshot in the same transaction. Events explain how the case got here; the snapshot makes reads fast. You can verify or rebuild the snapshot from events. This is event history plus a materialized current aggregate, not full event sourcing for every read. Never keep only a mutable status row.

Snapshot: CB-812   state=SUBMITTED   version=9   policy=v12
Events:   OPENED → PROVISIONAL_CREDIT_REQUESTED → PROVISIONAL_CREDIT_POSTED
          → EVIDENCE_ADDED → EVIDENCE_READY → ELIGIBLE → SUBMITTED

FinancialAction: intent here, posting there

The FinancialAction row and its stable ledger key are part of the case transaction. The remote ledger posting is not. The outbox delivers the command, and a later case event records the observed result. This avoids a distributed transaction while never forgetting intended work. Never hold the case DB transaction open across a ledger call.

The key is semantic. It names the business action being retried, not the HTTP request:

CB-812:PROVISIONAL_CREDIT:v1
CB-812:REVERSE_PROVISIONAL:v1
CB-812:FINAL_ADJUSTMENT:v2

Using the case id alone as the key is the classic mistake: one case legitimately needs several different financial actions.

Partial wins and multiple adjustments

Each approved amount and its financial consequence is a versioned FinancialAction linked to the case and to the prior action. A partial win records awarded amount, rejected amount, and the resulting adjustment. Never overwrite one "credit amount" field.

Evidence: metadata here, bytes there

Encrypted file bytes live in object storage. The case store keeps evidence id, object version, checksum, media type, scan status, uploader, timestamps, retention class and which network submission it went in. Access is through short-lived authorized download URLs and is logged. Never put large sensitive documents in general case rows.

Deadlines that change after a network response

Complete or cancel the old obligation through an event, then create the new deadline from the network response and the applicable policy version, in the same case commit. Keep both for audit. Calculate time zones and business calendars explicitly. Never mutate the original due date without history.

Concurrency: the case version

Case id is the aggregate key. Every command carries the expected case version. A conditional update accepts one command; a stale command reloads and re-evaluates. This is the same optimistic-concurrency trick as the ledger's account version, applied per case. A per-case queue is the alternative under high contention. Never serialize all cases globally.

Say it in 30–60 seconds

DisputeCase: the current summary of one dispute with its state, amount, country and policy version. CaseEvent: one immutable fact in its history. Deadline: a due time saved in the database with a type and a status. EvidenceItem: metadata pointing to an encrypted file in object storage, with a checksum and scan status. NetworkSubmission: the stable reference we sent and whether it was acknowledged. FinancialAction: one money step with its own ledger key. The case is the root; everything changes through commands, never by editing a status column.

Interview sentence

"The case is the aggregate root; state changes happen through commands rather than direct status updates."

6. The atomic case commit, and why side effects happen after

Stage 4: the simplest correct architecture.

What a command does

  1. Authenticate and authorize: who is issuing this command, and may they?
  2. Check request idempotency and the expected case version.
  3. Validate the transition against the current policy version for this country and network.
  4. In one commit, write: the new CaseEvent, the updated snapshot and version, any deadlines created or completed, the idempotency record, and the outbox rows for every side effect this transition implies.
  5. Return the accepted state, by name: "SUBMITTED", "PROVISIONAL_CREDIT_PENDING". Not an HTTP 200.

The case can never say "submitted" while forgetting that the network submission still needs to happen: the outbox row that says "submit this" is in the same commit as the state that says "submitted".

Why side effects happen afterwards

The card network, the ledger, object storage and the notification service are independent systems with their own latencies and failures. Holding a database transaction open while calling them is slow and fragile, and it creates the exact "half done" states you are trying to eliminate. So:

commit durable intent → return accepted state → worker performs external action → record observed result as a new event

That last step is what distinguishes this from the ledger's outbox: here the worker's observation comes back into the case. The network acked, the ledger posted transaction tx_9182, the scan passed. Each is a CaseEvent, so the case's own history says what actually happened outside it.

The pieces around the commit

  • Timer: wakes workers near a due time. Efficient for normal processing.
  • Sweeper: periodically queries durable deadlines for due and near-due rows and catches anything the timer missed. The safety net.
  • Search index: Operations searches by country, age, reason, deadline, assignment. Built from case events through the outbox. Ops reads the index to find a case, then opens the authoritative case by id before acting. Index lag is visible and fine for discovery, never for transition validation.

The follow-ups

  • Why not a generic workflow engine for everything? Use one for timers, retries and orchestration if it helps. But the domain service still owns valid transitions, policy versions, audit and idempotency. The engine is execution infrastructure, not business truth. Never model critical policy only as opaque workflow configuration.
  • What is committed before you acknowledge? Event, snapshot and version, relevant deadlines, idempotency record, outbox intents. Then you can acknowledge durable acceptance even though side effects are pending. Never acknowledge SUBMITTED before the durable network-submission intent exists.
  • How does the sweeper avoid processing a case twice? It conditionally claims a due deadline using status plus lease or version, and the resulting command is idempotent. A duplicate worker either fails the claim or produces the same result. Expired leases let you recover from worker crashes. Never a process-local mutex.
  • Object storage succeeds but the case commit fails? The upload is orphaned and is not valid evidence, because no committed EvidenceItem references it. A lifecycle job deletes unreferenced uploads after quarantine. Use a staged upload token and checksum so the commit links the exact object version. Never mark evidence ready because bytes exist.
  • Which parts may be eventually consistent? Search, analytics, notifications, customer summaries. Not: case transitions, expected version, deadline creation, idempotency, financial-action intent. External network and ledger outcomes are asynchronous but explicitly represented as Pending or Unknown; eventual consistency is not the same as unmodeled unknown state.

Say it in 30–60 seconds

A command arrives. I check permission, the idempotency key and the expected case version. I validate the step against the current policy version. In one commit I save the new event, the updated snapshot, any deadlines and the outbox rows. I reply with the new state. After the commit, workers call the card network, the ledger, object storage and notifications, and record what they observed as new events. A timer wakes workers near a due time; a sweeper reads the saved deadlines and catches anything the timer missed. Search for Ops is a separate index built from events.

Interview sentence

"A case command commits workflow state and intent locally; external side effects happen after commit."

7. Deadlines: timer plus sweeper

Why the design refuses to trust a scheduler.

A card network gives the issuer a fixed window to respond; miss it and the dispute is lost regardless of merit. That makes a deadline a legal and financial obligation, not a convenience. The design treats it accordingly:

  • The Deadline is a row, written in the same commit as the transition that created it. If the process dies a millisecond later, the row exists.
  • A timer (a scheduler, a delayed queue, a workflow engine) wakes a worker near the due time. This is the fast path.
  • A sweeper runs every few minutes, queries deadlines that are due or near due and not yet claimed, claims them conditionally, and processes them. This is the path that still works when the timer infrastructure has lost everything.
  • Claims use a lease: UPDATE deadline SET status='CLAIMED', lease_until=now()+5min WHERE id=? AND status='OPEN'. Zero rows updated means someone else has it. An expired lease means the previous worker died and the work is available again.
  • Alerts fire before breach (time-to-breach below threshold with the case not progressed) and after (breached and not escalated). Metrics: oldest unprocessed deadline, count near breach.

When the network responds, the old deadline is completed by an event and a new one is created from the response window under the applicable policy version, in the same commit. Both stay for audit.

Avoid saying

"The scheduler will trigger it." One in-memory scheduled job is a best-effort timer; the row is the obligation. And never rebuild deadlines from memory after a restart.

Interview sentence

"Timer delivery is an optimization; durable deadline rows plus an independent sweeper are the safety net. I measure oldest unprocessed deadline and time-to-breach."

8. Evidence

Large, sensitive, legally significant files, handled without contaminating the case store.

The lifecycle

staged upload (token + checksum) → UPLOADED → scan (format, malware, checksum) → EVIDENCE_READY
                                                     ↘ QUARANTINED (never usable; customer asked for a replacement)
  • Bytes go to encrypted object storage via a staged upload that returns a token and a checksum. The case commit links exactly that object version; if the commit fails, the object is an orphan and a lifecycle job deletes it after quarantine.
  • Metadata lives in the case store: evidence id, object version, checksum, media type, scan status, uploader, timestamps, retention class, and which network submission included it.
  • Usable means EVIDENCE_READY. Bytes existing is not enough; the file must pass checksum, format, malware and access checks first. A failed scan leaves it UPLOADED or QUARANTINED and the case cannot submit it. Record the scan result without exposing the unsafe content, and don't let failed scans be overridden casually.
  • Replacement is a new EvidenceItem version linked to the prior one. The old object is immutable. The case records which version went to the network.
  • Access is via short-lived authorized URLs, logged. Deletion follows retention and legal-hold policy, never a user's whim while a case is live.

Interview sentence

"Uploading bytes is not evidence. A file becomes evidence when a committed EvidenceItem references an exact object version that has passed checksum, format and malware checks."

9. Provisional credit: the deep dive

Stage 5: where long-running case state meets customer money.

The lifecycle

  1. Policy (by product, jurisdiction, risk) says Ana is owed provisional credit for the disputed R$300.
  2. The case commit saves a FinancialAction with key CB-812:PROVISIONAL_CREDIT:v1, state REQUESTED, and an outbox row. Case state becomes, say, UNDER_REVIEW with financial state PROVISIONAL_CREDIT_PENDING.
  3. After commit, a worker sends that command to the ledger. The ledger posts a balanced transaction (Ana +300, a disputes-clearing or provisional-credit expense account −300) and returns tx id. The worker records PROVISIONAL_CREDIT_POSTED as a case event with the ledger's transaction id.
  4. Outcome arrives from the network:
    • Win in full: finalize. The credit stands; a finalization action may move the clearing side to the recovered-from-network side.
    • Loss: CB-812:REVERSE_PROVISIONAL:v1 asks the ledger for a linked reversal (Ana −300). The original posting is untouched.
    • Partial win (R$200 of 300): compute the final entitled amount, compare with what was provisionally posted, and create one linked adjustment for the difference: CB-812:FINAL_ADJUSTMENT:v2 for −100. Handle currency and rounding explicitly.
  5. The case closes only when policy says both are complete: the workflow decision (WON / LOST / PARTIAL) and the financial settlement (all required ledger actions confirmed).
  6. Reconcile three truths: the network's award, the case's recorded decision, and the ledger's postings. They must agree on outcome and amount.

Case state is not money state

A case can be decided while the ledger action is still pending. Expose both to Operations and to customer messaging. Otherwise the UI can say "completed" while the customer has neither received nor repaid the money. One status field for legal outcome and money completion is the mistake.

The follow-ups

  • The customer spends the provisional credit and then loses. The reversal may create a debt or a negative available balance, according to product, regulation and hardship policy. The platform records the loss, asks the ledger for the linked reversal, and presents a clear repayment or negative-balance experience. Risk policy may cap credits or delay availability, but that's a business choice. Never assume the system can simply take money that isn't there.
  • How do you know whether a timed-out ledger credit was posted? Query or retry the exact same semantic FinancialAction key. The ledger returns the prior transaction if it committed, or safely creates it if not. The case stays FinancialSettlementPending until a durable result is observed. Never infer failure from a timeout; never issue a new key.
  • Is winning the same as settlement? No. WON is a workflow decision; FinanciallySettled means all required ledger actions are confirmed and reconciled.
  • The network award conflicts with our recorded outcome. Put the case in a reconciliation-exception state, preserve both facts, stop automatic closure, route it to an owned queue. After investigation, issue an auditable correction event and any required ledger adjustment. Alert by amount, age and deadline impact. Never silently make one record match the other.
  • Who may issue a manual credit or reversal? Only a narrowly authorized Operations role through a controlled command, with reason, evidence, amount limits and immutable audit. High-value actions need a second approver; the ledger independently enforces allowed command types. Engineers and DBAs do not bypass the workflow. No unrestricted manual balance editing.

Say it in 30–60 seconds

Provisional credit is where long-running case state meets customer money. When policy allows it, the case commit saves a FinancialAction with a key like CB-812:PROVISIONAL_CREDIT:v1, and the outbox sends that command to the ledger. If we win, we finalize. If we lose, we ask the ledger for a linked reversal. If we win partially, one adjustment for the difference. Case state and money state stay visibly separate: "won" is a decision, "financially settled" is a fact. At the end I reconcile three truths: the network's award, our case decision, and the ledger posting.

Avoid saying

Trusting a workflow status as proof that money was posted. Editing the original credit amount. Using the case id alone as the ledger key.

Interview sentence

"I'll expand provisional credit because customer money and long-running case state meet here. The key explains which business action is being retried, and won is a decision while financially settled is a fact."

10. Batch files to the network: the CSV / FTP variant

A 2026 candidate was asked to design the chargeback ingest system that writes disputes to CSV, uploads by FTP to Mastercard four times a day, and takes the network's answers back the same way. This is what the prompt looks like end to end.

The end result

Four times a day the platform gathers every case that is ready to go, writes them into one file with a stable id per row and a stable id for the file, uploads it, and records that it did. Later a file comes back; every row in it is matched to something we sent, turned into a case command with the row's own id as the key, and anything we sent that never gets answered ages in a reconciliation queue until someone looks at it.

The nouns this adds

BatchRunOne scheduled cycle: id like 2026-09-06-14 (date and slot), the file name, the row count, a checksum of the file, and a status: BUILDING, UPLOADED, ACKNOWLEDGED, FAILED. Written to the database before the file leaves.
BatchRowOne case's line in one file: the case id, the NetworkSubmission reference from section 5, the run it went out in, and a status: QUEUED, SENT, ANSWERED, REJECTED. The row id is the NetworkSubmission reference; that is what makes retries safe.
InboundFileA file we received: its name, checksum, when it arrived, how many rows parsed, how many quarantined. The original bytes are kept in object storage untouched.
ReconciliationItemA row we sent that has no answer yet, with the time it was sent. Aged continuously.

DisputeCase, CaseEvent, Deadline, EvidenceItem, NetworkSubmission and FinancialAction are unchanged. The file is a delivery mechanism, not a new kind of truth.

One day, walked through

  1. 13:58. Ana's case CB-812 reached ELIGIBLE this morning; its Submit command created NetworkSubmission NB-CB-812-1 in state QUEUED. Two hundred other cases are in the same state.
  2. 14:00, claim. The batch job creates BatchRun 2026-09-06-14 and, in one database transaction, claims every QUEUED submission by setting it to SENT-IN-RUN 2026-09-06-14 with a conditional update (only rows still QUEUED). A second job starting by accident claims zero rows and does nothing.
  3. 14:00, build. The job reads the claimed rows, writes the CSV deterministically (sorted by row id, fixed columns, fixed encoding), computes a checksum, stores the file in object storage, and records the checksum and row count on the run. Building is repeatable: the same claimed rows always produce the same bytes.
  4. 14:01, upload. FTP the file under a name derived from the run id. Mark the run UPLOADED with the server's response. The rows are now AWAITING_ANSWER and each one becomes a ReconciliationItem.
  5. 14:01, tell the case. One CaseEvent per row, SUBMITTED_IN_BATCH 2026-09-06-14, through the normal command path, so the case history says exactly which file carried it. Complete the "submit by" deadline; open the "expect network answer by" deadline from policy.
  6. Next morning, 07:00. A response file appears on the FTP. Download it, checksum it, store the original. Check the file id against InboundFile; if seen, stop, this is the same file delivered twice. Parse it row by row. Each good row references our row id NB-CB-812-1 and carries an outcome (accepted, rejected with reason code, or a later award). It becomes a case command with idempotency key file-id:row-id. Each bad row (unknown reference, malformed, wrong amount) goes to a quarantine table with the raw line and a reason; the file's other rows still process.
  7. 07:02. CB-812's row says "accepted". Its ReconciliationItem is closed, a NETWORK_ACKED event is appended, and the deadline moves to the merchant's representment window. A row for CB-640 says "rejected: invalid reason code" → event NETWORK_REJECTED, case goes back to an Ops queue with the reason, no new submission until a human fixes the input.
  8. Every hour. A reconciliation sweeper ages every open item. Anything older than the expected answer window (say, two cycles) is alerted on; anything approaching a dispute deadline is escalated. Operations sees both count and age of the oldest item.

Idempotency at three levels

LevelStable identityWhat it prevents
RowNetworkSubmission reference, e.g. NB-CB-812-1, unique per case and attemptThe same dispute appearing in two files. A case can only be claimed into one run while QUEUED.
FileRun id → file name and checksum; inbound file id from the networkRe-uploading a file on retry creates a second file; re-processing a response file processes rows twice.
RunRun id derived from date and slot, unique constraintTwo schedulers building the 14:00 batch. The second insert fails; it does nothing.

The command that each inbound row becomes carries file-id:row-id as its key, so even if the file is re-processed after a crash halfway through, rows already applied return the prior result and rows not yet applied get applied once.

What must be strongly consistent, and what may lag

  • Strong: the claim (which rows are in which run), the run status, the per-row status, the inbound file dedupe, the case commands. All of it lives in the case database.
  • May lag: the Ops dashboard of batch health, the search index, the daily reconciliation report.
  • Unknown, modelled explicitly: a row that was uploaded but not yet answered. It is not "failed" and it is not "done". It is AWAITING_ANSWER with an age, and the customer sees "sent to the card network, awaiting response".

The failures the interviewer will insert

Upload times outUnknown, not failed. The file may be on the server. List the remote directory for the run's file name; if present and the size and checksum match, mark UPLOADED. If absent, re-upload the same file under the same name. Never rebuild with a new run id, that would resend 200 disputes.
Job crashes mid-buildRows are claimed, no file uploaded. On restart the job finds a run in BUILDING, rebuilds the file deterministically from the claimed rows, and continues. If a run is stuck in BUILDING past a threshold, alert; an operator can release the rows back to QUEUED with an audited command.
Response file arrives twiceSame file id and checksum → stop. Same name, different checksum → this is a new version; quarantine both, alert, human decides. Never silently apply the second.
Half the rows are garbageProcess the good rows, quarantine the bad ones with the raw line, alert on quarantine count. Never reject the whole file because of one row, and never guess what a malformed row meant.
A row references a case we don't knowQuarantine with reason UNKNOWN_REFERENCE. It could be a network error, a case from another environment, or a bug in our own reference format. Ops resolves it; the platform does not invent a case.
The 14:00 slot is missedDeadlines are rows, not timers. The next run picks up everything QUEUED; the deadline sweeper flags any case whose "submit by" date now falls before the next slot and escalates it for a manual out-of-cycle submission.
No response file for two daysNothing about our cases is wrong. The reconciliation queue grows, its oldest-item age crosses the threshold, someone pages the network team, and any case approaching its dispute deadline is escalated with evidence of the upload.
Volume goes up tenfoldThe file is bigger; nothing structural changes. Build streams rows instead of loading them all; if a single file exceeds the network's size limit, split into numbered parts under one run (2026-09-06-14-part-3); parse inbound files in parallel by row range since each row's command is independently idempotent. The one thing that cannot scale by adding workers is the claim step, and that's one indexed conditional update.

Why files at all, and what to say if asked

Because the counterparty decided. Card networks and many banks still run scheduled file exchange for dispute processing, and the issuer doesn't get to choose the protocol. The design response is to treat the file exactly like any other unreliable external call: durable intent before sending, stable identity per unit of work, observation recorded as events, unanswered work aged and visible. If the network offers a real-time API later, only the adapter changes; the case model and the reconciliation model stay.

Say it in 30–60 seconds

Four times a day I claim every case that is ready, in one transaction, into a batch run with an id made from the date and the slot. I build a CSV deterministically from the claimed rows, each row carrying the case's stable submission reference, upload it under a name derived from the run id, and mark the run uploaded. Every row is now "awaiting answer" and sits in a reconciliation queue. When a response file arrives, I dedupe it by file id, parse it row by row, quarantine bad rows without dropping the file, and turn each good row into a case command keyed by file id plus row id. Anything sent and unanswered ages; the age of the oldest item is what pages someone. A timeout on upload is unknown, not failed: I check the remote directory before I re-upload the same file, and I never rebuild with a new run id.

Interview sentence

"The file is just a slower, batched version of an external call. Durable intent before sending, a stable identity per row and per file, answers recorded as events, and everything unanswered aged in a reconciliation queue."

Avoid saying

"Retry the upload with a fresh file." That resends every dispute. "Reject the whole file if a row is bad." That blocks 199 good cases for one. "The cron job handles the schedule." The claim is a transaction and the deadlines are rows; the cron is just a trigger.

11. Failures

Stage 6: the hard failures are uncertain external outcomes and missed deadlines.

For every failure, six questions: what committed? what retries, with which identity? what can duplicate? what does the customer see? which metric alerts? what is the safe operator action?

FailureWhat you do
Network timeoutTimeout means unknown, not failed; the network may have processed it before the response was lost. Query with the same external reference. If the network supports idempotent resubmission, retry with that reference; otherwise escalate before creating another submission. Persist every attempt and response for reconciliation and deadline evidence. Never resubmit with a new reference.
Ledger timeoutRetry the same FinancialAction key. The ledger returns the prior posting or performs it once. Case stays settlement-pending until observed.
Timer workers down an hourDeadlines live in the database. Recovery workers sweep due and near-due rows, claim them conditionally, process idempotently, escalate breaches. Measure oldest unprocessed deadline and time-to-breach. Never rebuild deadlines from memory.
Two operators decide concurrentlyBoth commands carry the expected case version. One commits; the other gets a conflict, reloads, and is rejected or consciously retried. The audit trail shows both attempts without two decisions applied. Never last-write-wins.
Malware scan failsEvidence stays UPLOADED or QUARANTINED, never READY. The case cannot submit it; the customer gets a safe replacement request; the file is isolated or deleted per security policy.
Bad policy release misclassified 5,000 casesFreeze that policy version for new evaluations. Identify affected cases by version. Classify impact. Run an approved remediation command that appends corrective events and financial actions. Notify customers and regulators as required. Reconcile every corrected case and review why tests and rollout gates failed. Never rewrite event history or bulk-edit statuses.
Network unavailable near deadlinesKeep durable case state and stable submission identity, queue the work, show Reviewing or Delayed, and trigger the escalation and alternate operational procedure for cases approaching breach.

Volume goes up tenfoldThe case store scales by case id (no cross-case transactions). Workers scale horizontally because every side effect is idempotent. Search moves fully to the projection. Batch files split into numbered parts under one run. What does not scale by adding machines is Operations, so the automation-versus-review trade-off in section 12 is the real answer.

The dashboard that tells dependency failure from internal backlog

Show external request latency and status per dependency (network, ledger, storage) next to internal queue age, worker throughput, error rate, lease saturation and outbox lag. External latency up while queue processing is healthy: dependency failure. Queue age up while dependency latency is normal: internal capacity or code. Add deadline and customer-impact views to both. One overall error-rate chart tells you nothing useful.

Say it in 30–60 seconds

Timeouts mean unknown, not failed. Network timeout: query the same external reference before resubmitting; a new reference could open a second dispute. Ledger timeout: retry the same action key. Timer workers down for an hour: the sweeper reads saved deadlines and escalates the ones close to breach. Two operators act at once: the expected version accepts one and rejects the other. Malware scan fails: the file stays quarantined, never "ready." A bad policy release: freeze that version, find affected cases by version, fix forward with audited events.

Interview sentence

"For each failure I'll state what committed, what retries with which stable identity, what can duplicate, what the customer sees and who is paged. The hard failures here are uncertain external outcomes and missed deadlines."

12. Rollout and ownership

Stage 7: how to reach the design safely, and who owns what.

Launch narrowly

  1. One country, one network, one reason-code family. Choose the lowest-risk, well-understood combination with meaningful volume, a cooperative Operations owner, stable network certification and limited financial exposure. The exact choice needs business data, not a guess; don't pick the biggest market for prestige.
  2. Shadow the eligibility and deadline maths. Copy production inputs to the new decision engine, suppress all side effects, store shadow outputs separately, compare eligibility, required evidence, deadlines and reasons against the authoritative process. Shadow processing must be unable to emit network or ledger commands, and it never writes to live case state.
  3. Then enable network submissions, then financial actions, each behind its own kill switch.
  4. Kill switch and draining. A kill switch stops new external side effects but keeps durable intents and in-flight states visible. Let safe acknowledgements and observations drain, pause unsafe retries, resume from the outbox after remediation. Separate switches can control network submission, credits and notifications independently. Never kill workers and lose track of committed intent.

Who owns what

PlatformCase mechanics: transitions, audit, deadlines, APIs, idempotency.
Legal / complianceRule meaning: eligibility, statutory deadlines, evidence requirements, versioned and approved.
OperationsQueues, exception procedures, the 3 a.m. decisions.
Network teamsAdapters, message formats, certification.
Ledger teamMoney correctness; independently enforces allowed command types.
ProductWhat the customer reads, when they see money, and the Processing / Delayed states.

Centralize mechanics, not meaning

Centralize stable mechanics and a governed policy framework. Country owners publish versioned rule packages under common contracts, tests, audit and rollout controls. This balances consistency with local legal accountability. Don't fork the platform, and don't force every rule into global code.

The biggest trade-off: automation versus human review

Automate only what shadow results prove you can measure: precision and recall by reason and market, low financial-loss and customer-harm rates, deadline compliance, explainable decisions, stable data quality. Automate gradually with thresholds, confidence bands, sampling and easy human escalation. Not because average handle time improved.

Say it in 30–60 seconds

Launch one country, one network, one reason-code family. Shadow the eligibility and deadline maths first, without touching live cases. Then enable network submissions, then money actions, each behind its own kill switch that stops new side effects but keeps committed work visible. Platform owns mechanics; Legal owns rule meaning; Ops owns queues; the Ledger team owns money; Product owns what the customer reads. Biggest trade-off: automation versus human review; automate only what shadow results prove we can measure.

Interview sentence

"The platform should centralize stable mechanics, while jurisdiction-specific policy remains explicitly owned and versioned."

14. Practice next

How to drill this alongside the ledger.

Run the two mocks back to back. The seven stages are identical; only the nouns change. Practise saying each stage's 30–60 second version out loud with a timer, then take the follow-ups without notes. The ones this material should let you take cold:

  • Issuer versus acquirer, and why you default to issuer.
  • Why opening a case doesn't move money.
  • Request idempotency versus business uniqueness for duplicate disputes.
  • Event plus snapshot versus a mutable status row.
  • Why FinancialAction intent is in the commit but the ledger posting is not.
  • How the sweeper claims work without double-processing.
  • What happens when object storage succeeds but the commit fails.
  • Win, loss and partial win as linked postings, never edits.
  • Network timeout: query by reference before resubmitting.
  • Remediating a bad policy version without rewriting history.
  • Kill-switch behaviour for in-flight cases.

Drill the interruptions

Set a timer for 40 minutes and have someone (or a script) inject one of these every ten minutes, at random, while you are mid-sentence. Answer it with the six questions, then return to your thread out loud.

  • "Volume just went up tenfold." (Ask: tenfold what?)
  • "This is too slow. How do you improve performance?"
  • "The card network is unreachable for the rest of the day."
  • "The ledger is timing out on every credit."
  • "A regulator wants this case exactly as it stood on 3 June."
  • "Two operators just decided the same case at the same second."
  • "The response file has 4,000 rows and 300 of them are garbage."
  • "We're launching in Colombia next month with a different network."

If the interviewer changes the prompt mid-way (a loan-collections workflow, a KYC review queue, a fraud-alert case system, or the batch-file version of this one), keep the seven stages and swap the nouns: it is still a case-management system with durable obligations, versioned policy, idempotent side effects and money it asks the ledger to move.

15. Glossary, from zero

Every term this guide uses, explained as if you'd never heard it. Grouped by theme; each entry says where the term shows up.

The card-dispute business

ChargebackWhen a cardholder says "I didn't make this purchase" or "I paid but never got the goods", their bank can pull the money back from the merchant's bank through the card network. That reversal is a chargeback. The whole process around it is a dispute.
IssuerThe bank that gave the customer the card. Nubank is the issuer for Ana. The issuer is the one who receives the complaint and files the dispute.
AcquirerThe merchant's bank; the one that "acquires" card payments on the merchant's behalf. It receives the dispute and defends the merchant.
Card networkVisa, Mastercard, Elo. They don't hold anyone's money; they set the rules, carry the messages between issuer and acquirer, and arbitrate when the two disagree.
Reason codeA short code the network defines for why a dispute is being raised: "fraud, card not present", "goods not received", "duplicate charge". Each code has its own deadlines and evidence rules.
RepresentmentThe merchant's reply: "here is proof the customer did buy this". It re-presents the transaction. The issuer then has a window to respond again.
Arbitration / awardWhen issuer and acquirer can't agree, the network decides. Its decision is the award: who wins, and for how much.
Provisional creditMoney the issuer gives the customer up front, while the dispute is still open, so they aren't out of pocket for weeks. "Provisional" because it may be taken back if the dispute is lost.
Partial winThe network awards part of the disputed amount. If Ana disputed R$300 and gets R$200, the issuer has to adjust the provisional credit by the R$100 difference.
Statutory deadlineA deadline set by law or regulation (not just network rules). Miss it and there may be legal consequences, not only a lost dispute.
Retention / legal holdHow long you must keep documents (retention), and a rule that says "don't delete this, it may be needed in a legal matter" (legal hold).
PIIPersonally identifiable information: names, document numbers, addresses. Must be protected; must not leak into logs.

How money is represented

LedgerThe system that records every movement of money and knows every balance. The chargeback platform never moves money itself; it asks the ledger to.
Entry / postingOne recorded line of money movement against one account. "Posting" is the act of writing entries. Once posted, an entry is never edited.
Posted balanceThe sum of all entries on an account. The money that has actually moved.
HoldA reservation. A card purchase first places a hold ("R$80 is spoken for") and only later becomes a real posting when the merchant settles.
Available balancePosted balance minus open holds. The amount the customer can actually spend right now.
Linked reversalUndoing a posting by writing a new, opposite entry that points at the original. The original stays in the history. Never done by deleting or editing.
AdjustmentA new posting for the difference between what was credited and what turned out to be owed, for example after a partial win.
Clearing accountA holding account that money sits in while a multi-step operation is in flight. It makes the "in between" state real and visible instead of the money being nowhere.

Databases and consistency

Transaction (database)A group of database writes that either all happen or none happen. Not to be confused with a card transaction (a purchase). In this guide, "one commit" and "one transaction" mean the database kind.
Atomic / atomic commit"Atomic" means indivisible. An atomic commit is a transaction that finishes completely or not at all; there is no moment where half of it is saved.
CommitThe instant a database transaction becomes permanent. Before commit, nothing has happened; after, it survives crashes.
RollbackCancelling a transaction before commit so nothing it wrote is kept.
Row / table / columnA table is a spreadsheet-like structure; a row is one record in it; a column is one field. "A deadline is a row" means it's a saved record, not something floating in memory.
IndexA lookup structure that lets the database find rows by a column quickly, like a book's index. "Index on (status, due_at)" means "make it fast to find rows with a given status and due time".
Unique constraintA rule the database enforces: no two rows may have the same value in this column. Used to guarantee an idempotency key or a run id can only exist once.
Conditional updateA write that only happens if some condition is still true: "update this case, but only if its version is still 7". If someone changed it in between, the update does nothing and you know.
Version (on a case or account)A counter that goes up by one every time the record changes. Commands say "I read version 7"; the conditional update checks it's still 7. This is how two people acting at once can't both win.
Optimistic concurrencyLetting everyone read freely and only checking for conflicts at write time (with the version). "Optimistic" because you assume conflicts are rare.
Row lock / SELECT FOR UPDATEThe pessimistic alternative: grab the row so nobody else can touch it until you're done. Simpler, but people wait, and locks can deadlock.
DeadlockTwo operations each waiting for a lock the other holds, forever. Avoided by always taking locks in the same order.
Lease / claimA short-lived ownership: "I'm working on this deadline for the next five minutes." If the worker dies, the lease expires and someone else can pick it up. Prevents two workers doing the same job.
SKIP LOCKEDA database option meaning "give me rows to work on, but skip any that another worker already grabbed". The standard way for many workers to share one queue table.
Strong consistencyEvery read sees the latest committed write. What you need for anything that decides: case transitions, deadlines, money.
Eventual consistencyReads may be a little behind for a while but will catch up. Fine for things you only look at: search, dashboards, notifications.
Source of truth / authoritativeThe one place a fact is decided. Everything else is a copy that can be rebuilt from it.
Distributed transaction / 2PCTrying to make one atomic commit across two separate databases. Two-phase commit (2PC) is the classic protocol for it: "everyone prepare", then "everyone commit". Works, but blocks and is painful to recover. This guide avoids it by giving each system its own commit and linking them with keys and events.
SagaA multi-step operation where each step is its own commit, progress is saved, and a failed later step is undone by a compensating step (a linked reversal), not by rolling back.
Partition / shardSplitting data across several databases by a key (case id, customer id) so each one handles a share. "Hot partition" is one shard getting far more traffic than the others.
NoSQLDatabases that aren't traditional relational tables (key-value, document stores). Often cited as a scaling fix; in this guide, "move to NoSQL" is a wrong answer because the store isn't the bottleneck.
Datomic / ClojureNubank's database and programming language. Datomic never overwrites data; it keeps every past value, which is why "reproduce the case as of a date" is natural for them. Clojure is a functional language on the JVM. You don't need either; you need to know why they chose them (immutability).

Events, queues and workers

EventA record that something happened: "case opened", "network acknowledged". Written once, never changed. The case's history is its list of events.
Snapshot / aggregateThe current summary of a case, kept alongside the events so you don't have to replay the whole history to know its state. Can always be rebuilt from the events.
Aggregate rootThe one entity that owns a group of related records and is the only door for changing them. Here, the case: you change the case through commands, never by editing an event or a deadline directly.
CommandA request to change something: "open a dispute", "submit to network". Commands are validated; events are what gets recorded when a command is accepted.
Event sourcingStoring only the events and deriving all state from them. This guide uses events plus a snapshot, which is event history without making every read replay it.
Projection / read modelA copy of data shaped for a particular question (the search index, the Ops dashboard), built from events. Can lag; can be thrown away and rebuilt.
Idempotent / idempotencyDoing the same thing twice has the same effect as doing it once. Sending "credit Ana R$300" twice must credit her once. Achieved with an idempotency key.
Idempotency keyA stable identifier that travels with a request so the receiver can recognise a repeat. Generated once where the intent is born; reused on every retry.
Semantic keyAn idempotency key that names the business action, like CB-812:PROVISIONAL_CREDIT:v1, instead of a random id. It tells you what is being retried.
OutboxA table where you write "send this message later" in the same commit as the change it describes. A worker then sends it. Guarantees you never record a change without its message or a message without its change.
KafkaA system that stores streams of messages durably and in order and lets many consumers read them. Nubank uses it to move events between services. It is not a database and not the source of truth.
Topic / partition (Kafka)A topic is a named stream; it's split into partitions so it can be spread across machines. Messages with the same key go to the same partition, so they stay in order.
ConsumerA program that reads messages from Kafka and does something with them, like updating the search index.
At-least-once deliveryA guarantee that every message will arrive, possibly more than once. The normal case. It's why consumers must dedupe.
Dedupe (deduplicate)Recognising and ignoring a repeat, usually by remembering the ids you've already handled.
Correlation idAn id attached to a request that follows it through every service and message, so you can trace what happened where. Nubank's consumers dedupe on it.
WorkerA background program that takes jobs from a queue or table and does them: sends a file, calls the ledger, scans a document.
Timer / schedulerSomething that fires at a set time to start work. In this guide it's a convenience, never the thing that guarantees a deadline.
SweeperA worker that periodically scans the database for work that should have been done (due deadlines, unpublished outbox rows) and does it. The safety net under the timer.
Queue age / lagHow long the oldest unprocessed item has been waiting. The single most useful health number for any queue.
BackpressureSlowing down producers when consumers can't keep up, instead of letting the backlog grow without limit.
Dead-letter topicWhere a message goes when a consumer keeps failing on it, with the error attached, so it isn't lost and a human can fix and replay it.
Circuit breakerWhen a downstream call keeps failing, stop calling it for a while (pause the consumer) instead of hammering it. Turns a storm of errors into a queue that drains later.
Poison row / messageOne item that fails every time it's processed and would block everything behind it if you let it.
ReplayRe-reading events from the beginning (or from a checkpoint) to rebuild state. Safe because consumers are idempotent.
Fix forwardCorrecting a mistake by adding new events and postings that repair it, rather than deleting or editing history.

Files, storage and evidence

Object storageA service for storing files (S3-style): you put bytes in, get a reference back. Built for big files; not a database.
Staged uploadUploading a file to a temporary spot first, getting a token that identifies it, then linking it to the case in a commit. If the commit fails, the file is an orphan and gets cleaned up.
ChecksumA short fingerprint computed from a file's bytes. If the bytes change, the checksum changes. Used to prove you got the exact file you expected.
Malware scanChecking an uploaded file for viruses or malicious content before anyone opens it.
QuarantineSetting something aside as unusable pending review: a file that failed its scan, a file row that couldn't be parsed.
Short-lived URLA download link that only works for a few minutes and only for the person it was issued to. How evidence is served without exposing storage.
OrphanA file (or record) that nothing references, usually because the step that should have linked it failed.
CSVComma-separated values: a plain text file where each line is a record and fields are separated by commas. The simplest possible data file.
FTP / SFTPAn old, still widely used way to transfer files between organisations by uploading to and downloading from a server. Card networks still use it for batch exchange.
BatchProcessing many items together at a scheduled time instead of one at a time as they arrive.
DeterministicGiven the same inputs, always produces exactly the same output. A deterministic file build means rebuilding after a crash yields byte-for-byte the same file.
ReconciliationComparing two records that should agree (what we sent vs what they acknowledged; the network's award vs our decision vs the ledger's posting) and investigating every difference.

Measuring and operating

LatencyHow long one request takes, start to finish.
Throughput / TPSHow many requests per second the system handles. TPS is transactions per second.
p50, p99Percentiles of latency. p50: half of requests are faster than this. p99: 99% are faster; only 1 in 100 is slower. Engineers watch p99 because averages hide the slow cases customers actually notice. "p99 is bad" means the slowest 1% of requests are too slow.
Critical pathThe steps that must finish before the customer gets an answer. Anything on it adds latency; anything you can move off it makes the response faster.
Synchronous / asynchronousSynchronous: the caller waits for the result. Asynchronous: the caller gets "accepted" and the work happens later. The atomic commit is synchronous; calling the card network is asynchronous.
SLAService level agreement: a promised limit, like "a case reaches the network within one business day". Used to define when Processing has gone on too long.
MetricA number the system reports about itself continuously: queue age, error rate, p99.
Alert / page / on-callAn alert fires when a metric crosses a threshold. Paging means waking the on-call engineer, the person responsible for responding right now.
DashboardA screen of metrics for humans to watch.
EscalationHanding a problem to someone with more authority or a different team when the normal path can't resolve it in time.
RunbookThe written steps for handling a known incident, so the person on call at 3 a.m. doesn't have to invent them.
Kill switchA control that stops a feature or a side effect immediately (no more network submissions, no more credits) without stopping the whole system or losing saved work.
Shadow mode / shadow resultsRunning the new system alongside the old one on real inputs, but with all of its actions switched off: it computes what it would do and you record that. Then you compare its outputs (eligibility, deadlines, decisions) against what the trusted process actually did. "Shadow results" are those comparisons. You only trust the new system with real actions after the shadow results are good enough.
CohortA defined slice of customers (say, 1% in one city) you enable something for first, so a mistake affects few people.
Rollout / rollbackTurning something on gradually (rollout) and turning it back off if it misbehaves (rollback). Note: rolling back code is fine; "rolling back" committed money or history is not.
Precision and recallTwo ways to measure an automated decision. Precision: of the cases it flagged, how many were right? Recall: of the cases that should have been flagged, how many did it catch? You can't judge automation without both.
Four-eyesA rule that a sensitive action needs two people: one to do it, one to approve it.
Separation of dutiesMaking sure the person who can request something can't also approve it, and engineers can't bypass the workflow to edit money.
Audit / audit trailThe complete record of who did what, when, and why, kept so it can be checked later by someone outside the team.
Rate limitA cap on how many requests a caller can make per second. Mentioned in this guide only as something generic web-system designs obsess over and this round doesn't.
CacheA fast copy of data kept close to where it's needed. Great for display, dangerous for decisions, because a copy can be stale.
CDNContent delivery network: servers around the world that serve static files fast. Irrelevant to a dispute platform; another generic-design tell.
Horizontal scalingHandling more load by adding more machines doing the same job. Works for anything stateless and idempotent (workers). Doesn't work for the one thing that must decide (the write authority) or for people.

Architecture words

AdapterA small component that translates between your system and an outside one (the network's message format, the FTP server). Only the adapter changes when the outside changes.
Hexagonal architectureA way of organising a service so the business rules sit in the middle and every outside thing (database, network, queue) talks to them through adapters. Nubank uses it; it's why "only the adapter changes" is natural for them.
Policy / policy versionThe business rules (eligibility, deadlines, evidence needed), kept as versioned, testable code or configuration. Every decision records which version it used.
Workflow engineSoftware that runs multi-step processes with timers and retries for you. Useful as plumbing; must not become the owner of your business rules.
State machine / transitionA defined set of states (OPENED, SUBMITTED, WON) and the allowed moves between them (transitions). The case only moves through allowed transitions.
InvariantA rule that must be true no matter what breaks: "entries balance", "a deadline never disappears". You state them before designing so the design is judged against them.
BoundaryWhat this system owns and what it merely talks to. Deciding it first stops you rebuilding the ledger or the network by accident.
Fail closed / fail openWhat to do when you can't decide: refuse (closed) or allow (open). For money, closed is the safe default; open is a risk decision someone must own.
