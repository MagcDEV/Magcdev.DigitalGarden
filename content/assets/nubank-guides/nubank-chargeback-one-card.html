Chargebacks on one card

The chargeback guide is 15 sections. This is the part worth memorising, in plain words, in the order you will say it. If you can say everything on this page without looking, you can pass the round.

Condensed 1 October 2026 from The chargeback platform, end to end and the mock interview. Short on purpose: when something here feels thin, that is the section of the big guide to open.

1. The one sentence

A chargeback platform is a system that manages a case over weeks. It owns the story of the dispute: what happened, who did it, when, and under which rule. It asks other systems to do things: the card network to carry the dispute, storage to hold documents, the ledger to move money. It is not the ledger and it is not the network.

What it must never do: lose a deadline, forget a side effect it promised, lose the audit trail, or confuse "the case is won" with "the customer has been paid".

The sentence that ties everything together

"A case command commits workflow state and intent locally; external side effects happen after commit and come back as new events. Won is a decision; financially settled is a fact."

3. Step 1: questions, numbers, rules

Five questions, before anything

  1. Are we the issuer (the customer's bank) or the acquirer (the merchant's bank)? Assume issuer.
  2. Which countries and networks on day one? Each changes rules and deadlines.
  3. Who owns the rules and deadlines? Legal does; we implement them as versioned policy.
  4. Does opening a case move money? No. Provisional credit is a separate decision.
  5. What already exists? A ledger, a card transaction store, identity, storage, notifications. We integrate, we don't rebuild.

Plus one shape question: is the network a real-time API or files by FTP? Design for the API; say how a file changes it.

The features (what users can do)

A customer disputes a transaction and sees its status. An operator reviews evidence and decides. The platform submits to the network and records the outcome. The platform asks the ledger for credit, and for its reversal. Below the line: fraud scoring, the merchant side, reporting.

The numbers (ask for them first, then do the maths)

100M customers, 2B card transactions a month, 0.1% disputed
→ 2M cases a month ≈ 70k a day ≈ under 1 per second, ~8 at peak
20 events per case × 1 KB → 40 GB a month        (small)
2 files × 2 MB per case  → 8 TB a month          (object storage, not the DB)
30% need a human, 40 cases a day each → ~500 reviewers

The decision the numbers force

"Seventy thousand a day is under one write a second. One good relational database handles it, and would at ten times. This is not a throughput problem. It's a correctness, deadline and people problem, and that's where I'll spend the design."

The seven rules (the qualities, as rules)

  1. A case only moves through valid transitions, under a versioned policy.
  2. Every action records who, why, when. No anonymous status change.
  3. A deadline is a saved row. It cannot disappear if every worker dies.
  4. Every money action has its own key. A retry never credits twice.
  5. Every message to the network reuses the same reference. A new one could open a second dispute.
  6. Evidence is versioned and access-controlled. Old bytes are never overwritten.
  7. Every decision records the policy version that made it.

The scope sentence, at minute twelve

"I'll scope to the issuer-side workflow with provisional credit, because that's where correctness is hardest. The network is an adapter, the ledger is an existing system. Speed matters less than in payments; audit, deadlines and money correctness are strict."

4. Step 2: six nouns, three operations

DisputeCaseThe current summary: state, amount, country, network, owner, policy version. The row you read.
CaseEventOne fact in its history: opened, evidence added, submitted, won. Never edited. The snapshot can be rebuilt from these.
DeadlineA row with a due time, a type and a status. Not a timer in memory.
EvidenceItemMetadata about a document: where the bytes are, checksum, scan status, version. The bytes live in object storage.
NetworkSubmissionThe stable reference we sent to the network, and whether they acknowledged it.
FinancialActionOne money step with its own ledger key, like CB-812:PROVISIONAL_CREDIT:v1. We record the intent here; the ledger posts the money.

Three operations. Open a case (with an idempotency key from the app). Run a command on a case (type, expected version, reason, key). Read a case (snapshot, or history as of a date). Everything is a command on the case. Nobody edits a status column.

5. Step 3: the drawing

The version you name and don't draw: "One service, one table with a status column, synchronous calls to the network and the ledger, a cron for deadlines. It works for a week, then it fails audit, retries and deadlines. So I won't draw it."

The version you draw. A command comes in. Four things happen in order:

  1. Check: who is calling, the idempotency key, the expected case version.
  2. Validate the transition against the current policy version.
  3. One commit writes: the new event, the updated snapshot and version, any deadlines, the idempotency record, and outbox rows for every side effect.
  4. Return the new state by name: "submitted", "credit pending".

After the commit, workers read the outbox and call the network, the ledger, storage, notifications. Whatever they see comes back into the case as a new event: "network acked", "ledger posted tx 9182". So the case's own history says what happened outside it.

Two more boxes. A timer wakes workers near a due time; a sweeper reads the deadline rows every few minutes and catches what the timer missed. A search index built from events, for Ops to find cases; it may lag; Ops opens the real case by id before acting.

The key on every arrow. App → platform: the request key. Platform → ledger: the action key. Platform → network: the submission reference. File row: file id plus row id.

Say its cost, then its gaps

"It costs two writes per command instead of one, a worker fleet, and in-flight states the product has to show. It doesn't yet handle: deadlines beyond the timer, more than one money step per case, evidence trust, a file-shaped network, and the bad day. Those are my deep dives. I'd go deepest on provisional credit and failures."

The consistency line, said once: strong where I decide (transitions, deadlines, money intent); eventual where I only read (search, notifications, dashboards); explicitly unknown where the world hasn't answered yet.

6. The money story (Ana's R$300)

  1. Ana disputes R$300. Policy says she's owed provisional credit. The case commit writes a FinancialAction with key CB-812:PROVISIONAL_CREDIT:v1 and an outbox row. Case state: under review. Money state: credit pending.
  2. After commit, a worker sends that key to the ledger. The ledger posts +300 to Ana, −300 to a disputes clearing account, and returns its transaction id. A new event records it. Ana sees the money.
  3. Weeks later the network answers. Win: the credit stands. Lose: a new action REVERSE_PROVISIONAL:v1 asks the ledger for a linked reversal. Partial win (R$200 of 300): one adjustment FINAL_ADJUSTMENT:v2 for −100. Never edit the credit amount.
  4. The case closes only when the decision is recorded and every ledger action is confirmed, and three truths agree: the network's award, our decision, the ledger's postings.

Why the key is so specific

"One case legitimately needs several money actions. If the key were the case id, the reversal would look like a retry of the credit and the ledger would refuse it. The key names the business action being retried: this case, this action, this version."

Ledger timeout? "Unknown, not failed. I retry the same key. The ledger returns what it already posted, or posts once now. I never create a new key on a timeout; that's how a customer is credited twice."

7. When things break

For any failure, answer these six: What committed? What retries, with which key? What can duplicate? What does the customer see? Which metric alerts? What does an operator safely do?

FailureAnswer in one line
Network times outUnknown. Query by the same reference before ever resubmitting. Customer sees "sent, awaiting".
Timer workers down an hourDeadlines are rows, nothing lost. The sweeper claims each one with a lease, processes, escalates anything breached. Alert before breach.
Two operators, same case, same secondBoth carry the expected version. One commits; the other gets a conflict, reloads, sees it's decided. Never last-write-wins.
Upload succeeds, commit failsThe file is an orphan, not evidence. A cleanup job deletes it. Bytes existing is not evidence; a committed EvidenceItem that passed its checks is.
Bad policy release misclassifies 5,000 casesFreeze that version, find cases by version, fix forward with new audited events. Never rewrite history.
Operator credits a friendRoles and four-eyes above a threshold; actor on every event; the ledger independently limits what this platform may ask for.
Single point of failure?The case database's primary. Synchronous replica, automated failover in seconds; during it, commands get "try again", reads keep working.

Degrades, never dies. Network down: cases still open, submissions queue. Ledger down: decisions continue, credits pend with their keys. Storage down: uploads refused, nothing else. Search down: Ops works from queues. Kafka down: commands fine, notifications late.

8. "Ten times the volume"

  1. Ask what grew. Cases, documents, operators?
  2. Do the maths. 700k cases a day is 8 writes a second, 80 at peak. The database is still fine. Evidence storage becomes a cost. Operations becomes 5,000 people.
  3. Scale what scales: workers, adapters, the search index, storage. All idempotent, all horizontal.
  4. Say what doesn't: Operations. People don't scale by adding machines. The real lever is automation, decided from shadow results.
  5. Protect the rules while scaling. A "performance improvement" that bends one is a bug.

When they suggest caching the case

"I'd push back. Ops reads a case to decide on it, and a cached case is a stale decision input: two operators both read it, both think it's undecided. If it's read latency, I'd serve the snapshot from a replica and cache the versioned policy instead, because a version is a safe cache key."

9. Rollout, in three lines

One country, one network, one reason family. First shadow: run the new rules on real inputs with every side effect blocked, compare. Then enable network submissions behind a kill switch, then money behind its own. Legal owns the rules, Ops owns the queues, the ledger team owns money, we own the mechanics.

If the network is files: same case model. Add a BatchRun (one file, one upload, one status) and a reconciliation queue for rows not yet answered. Claim rows into a run in one transaction, build the file, upload under the run's name. A half-processed response file can be re-run safely because each row is keyed by file id plus row id. Upload timeout: check the remote directory before re-uploading the same file; never rebuild with a new run id.

10. Never say

  • "Opening the case credits the customer." (Credit is a separate policy decision.)
  • "The scheduler will handle the deadline." (The row is the obligation.)
  • "Resubmit with a fresh reference." (That can open a second dispute.)
  • "The case is won, so she's been paid." (Decision and settlement are different.)
  • "Roll back the policy and fix the statuses." (Fix forward, with events.)
  • "It'll be a lot of data, so we need something scalable." (Say the number and what it decides.)
  • "Let's cache the case." (A cached decision input is a stale one.)
