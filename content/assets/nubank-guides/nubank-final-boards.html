Which family?

The first question for any prompt you haven't seen.

Every Nubank prompt has one of two shapes. A money-moving system decides in milliseconds, so it copies the ledger. A long-running system manages a process over days, so it copies chargebacks. The generic prompts reuse the same habits with new nouns.

Say it

"Before I draw anything: is this system deciding about money in real time, or running a process over days? That tells me whether I need an authoritative aggregate with a version, or a case with events, deadlines and versioned policy."

1. Chargebacks Long-running

A dispute case that lives for weeks.

A chargeback platform manages a dispute case over weeks. Every change to a case is a command on that case. One commit writes the event, the snapshot, the deadline rows, the idempotency record and the outbox rows. After the commit, workers call the ledger, the card network and notifications, each with a stable key. Whatever the workers see comes back into the case as a new event. Deadlines are rows, so the sweeper finds them even when the timer dies.

Numbers70k cases a day is under 1 write a second. Not a throughput problem: a correctness, deadline and people problem.
KeysRequest key · action key CB-812:PROVISIONAL_CREDIT:v1 · submission reference NB-CB-812-1 · event id
DivesProvisional credit, then failures, then rollout in three lines

Say it

"A case command commits workflow state and intent locally; external side effects happen after commit and come back as new events. Won is a decision; financially settled is a fact."

2. Chargebacks, network by FTP Long-running

The same case model, when the card network takes a CSV four times a day.

Everything up to the outbox stays the same, and only the meaning of "send" changes. Four times a day, a batch run claims every ready row in one transaction. The job builds the file with the same bytes every time and uploads it under a name made from the run id. The answers come back the next morning as a file. Each good row becomes a case command keyed by file id plus row id. Bad rows go to quarantine, and every unanswered row ages in the reconciliation queue.

Numbers70k rows over 4 slots is about 18k rows per file, a few MB. Easy to build, painful to resend.
KeysRun id 2026-09-06-14 · row NB-CB-812-1 · file-id:row-id
TimeoutUnknown, not failed. List the remote directory, then re-upload the same file under the same name. Never a new run id.

Say it

"The file is just a slower, batched version of an external call. Durable intent before sending, a stable identity per row and per file, answers recorded as events, and everything unanswered aged in a reconciliation queue."

3. Ledger Money-moving

Every money movement as a pair of balancing entries.

A ledger writes every money movement as a pair of balancing entries, saved in one database commit. The transfer carries the client's key. The ledger looks up that key, then checks the accounts, the currency, the available amount and the account version. One commit writes the transaction, both entries, both account aggregates, the key record and the outbox row. The ledger returns "done" because the commit succeeded. After that, the outbox worker publishes to Kafka, and consumers build the feed and the statements.

KeysClient key K1 · transaction id to Kafka · K1:LEG_A, K1:LEG_B between shards · end-to-end id to the rail
DivesThe three timeouts, the hot account, the transfer across two shards

Say it

"Money becomes durable in the atomic store; events describe that fact afterwards. The idempotency key lives in the same commit as the money, so the same key always returns the same transaction."

4. Card authorisation and credit limit Money-moving

Approve or decline in a few hundred milliseconds, even at midnight with the cloud link down.

The card network asks "approve or decline?" and expects the answer in a few hundred milliseconds. One replica owns each account and keeps its available limit in memory, fed from an ordered log. An approval writes a hold and the decision in one atomic step, conditional on the account version. The hold lowers the available limit, not the posted balance. The ledger posts real entries only at capture. If the replica's lag or ownership is unknown, the replica declines.

Numbers2 billion a month is about 770 a second, some 8,000 at peak. A cross-region hop is 100 ms or more, so the decision stays local.
KeysThe network's reference, N1, on authorise and on capture
DivesAvailability at the edge versus truth of the balance, then failures

Say it

"Truth in the cloud, decisions at the edge, one fenced owner per account, and a measured link between them. A stale replica is how money gets spent twice, so unknown lag means decline, not guess."

5. Fraud decision in the payment path Money-moving

Allow, block or step-up, inside the authorisation budget.

A decision service returns allow, block or step-up in about 50 ms, and it never moves money. It reads features from a hot store, runs the rules and then the model. It records the decision, the feature snapshot and both versions before it returns. A slower lane on the event stream computes richer features, sends cases to review and joins the late labels. New rule and model versions come back through a shadowed rollout. When the model is down, a fallback decides, and Risk chooses its direction in advance.

NumbersAbout 8,000 decisions a second at peak, a 50 ms budget: a dozen feature reads and one small model
KeysThe caller's request key: the same key returns the same decision. Labels join by decision id.
DivesWhere synchronous stops, failures, and blocked payments that never label themselves

Say it

"The decision service decides inside the budget and never moves money. Every decision records its inputs, rules version and model version so it can be explained. Degraded mode is a deterministic fallback whose direction is a risk decision, and the feedback loop has to be designed because blocked payments never label themselves."

6. Sending a PIX to another bank Money-moving

The ledger, with a leg outside it.

We orchestrate PIX, and we don't rebuild it. One commit debits the customer into a clearing account and writes an outbox row. After the commit, an adapter submits to the rail with an end-to-end id that is made once per intent. The customer sees Processing until the rail answers. Each outcome is a new posting with its own key. A rail timeout is unknown, so the adapter queries by the same id and never submits again with a new one.

NumbersA few thousand sends a second at the 18:00 payday peak. The hot account is PIX clearing.
KeysThe customer's idempotency key · the end-to-end id E2E-1, reused on every attempt
DivesRail timeout, adapter crash after the commit, the hot clearing account

Say it

"One debit per command into clearing, one submission per intent with a stable end-to-end id, Processing until the rail answers, unknown after a timeout means query before retry, and daily reconciliation against the rail's own records."

7. Ride-hailing Generic

Match riders with nearby drivers.

Drivers report their location every few seconds, so the location stream is the scale problem. The system indexes drivers by geographic cell, and each matching service owns some cells. A match reads the rider's cell and its neighbours. One driver gets at most one active match, through a conditional claim on the driver record with a version. That claim is strong. The map of nearby cars is eventual.

Numbers1M drivers every 3 s is about 330k updates a second, 1.4 TB a day. Partition the location state by cell.
KeysThe rider's request key, so a retry after a matcher crash never matches twice
DivesThe hot cell, the staleness rule, two riders and one driver

Say it

"The claim on a driver is strong: a conditional write on a version, exactly like the case version. The map of nearby cars is eventual, and that's fine for something a rider only looks at."

8. Ad-click aggregator Generic

Count clicks per ad in near real time.

Clicks go to Kafka, partitioned by ad id. Stream processors keep a counter per ad per minute in memory, with checkpoints, and feed a fresh dashboard. The raw clicks also land in cheap object storage. A batch over that raw log closes each window after a grace period and gives the exact number for billing. So the dashboard is fresh and approximate, and the invoice is exact and late.

Numbers10k clicks a second, 100k at peak, about 100 GB a day raw. The raw log is the storage problem.
KeysThe click id, deduped within the window · a signed impression id checked before the stream
DivesNo lost clicks, one click per impression, the hot ad

Say it

"The stream gives freshness, the batch over the raw log gives exactness. I run both and reconcile them. The dashboard is eventual; the billing number is exact and comes later."
