How to read this sheet

Each step has a number, an action, and tags. A tag names the scored point that the step shows to the interviewer. The table at the end lists every scored point and the steps that cover it.

Three kinds of box repeat. A dark block is text you type: into NOTES.md, into Claude Code, or into the terminal. A green box is a line you say. "Done when" tells you that the step is finished.

Owning the plan: what to say

The interviewer can't see inside your head. They see that the plan is yours when it arrives before any planning prompt, when it carries reasons, and when you overrule the AI with a reason. Six signals show it:

  • You walk an example by hand before you design anything.
  • You name the hard part, and it is not the obvious part.
  • Each decision has a "because".
  • You name one alternative that you rejected, and its cost.
  • You say why the steps come in this order.
  • You change the plan when you learn something, and you say what changed.

The formula: ten parts, in the order you say them

Say these in the scope phase, in about two minutes in total. Skip a part when the problem doesn't need it. The slots change with the problem.

1 Understand: restate it

So the core of this is one sentence. The input is X, the output is Y, and the rule that matters is Z.

2 Prove it: one example by hand

Let me run one example by hand: input should give output, because rule. That example becomes my first test.

3 The hard part

The hard part isn't the obvious bit. It's the edge. That's where the bugs will be, so that's where the tests go.

4 The question that changes the design

One question changes the design: question? If yes, I'd A. If no, B.

5 Approach, and the alternative you rejected

I'll use approach because reason. I considered alternative. It buys benefit, but it costs cost, which we don't need here.

6 The data model

The core data is a map / a sorted list / a queue keyed by key, because the main operation is operation, and that makes it O(1) / O(log n).

7 The order, and why

I'll build it in this order: step 1 first, because everything else depends on it. Then step 2, then step 3. After step 1 we have something runnable and tested.

8 What "done" means

Done for this hour is scope, with tests. Extra is a stretch. If we get there, it slots in as where.

9 What could go wrong

What could go wrong: failure mode, so I'll mitigation. And in production I'd watch log / metric.

10 Agree

That's my plan. Does it match what you'd expect, or would you weight something differently?

Five scenarios, said out loud

Each scenario shows the full scope phase for one kind of problem: what you type, what you say, how you answer the AI's gaps, and the likely follow-up. Scenario A is the most likely shape: Nubank candidates in 2026 report small banking and in-memory database tasks that grow in levels.

A. A banking system that grows in levels

"Implement an in-memory bank: create accounts, deposit, transfer. Timestamps are passed in. More levels follow."

In NOTES.md (you type, in shorthand)

# Problem
In-memory bank: create, deposit, transfer. More levels later.
e.g. A=100, B=0, transfer 30 A→B → A=70, B=30, A.out=30

## Questions
- timestamps passed in? → yes, as args
- overdraft? → no: transfer fails
- transfer to same account? → fails
- amounts? → int cents
- operation IDs for retries? → answer

## Plan (each step starts with a failing test)
1. [ ] Create + Deposit → new, duplicate ID, unknown acct, amount ≤ 0
2. [ ] Transfer → ok, insufficient, same acct, unknown src/dst
3. [ ] TopSpenders(n) → by outgoing, ties by ID, n > count
4. [ ] run(): commands in → results out → integration

## Failure modes
- concurrency: one mutex on Bank (a transfer touches 2 accounts)
- retries: dedupe on operation ID, if they give one
- errors: returned; a transfer never half-applies

Say (about 90 seconds)

So this is an in-memory bank: accounts with balances, and operations that move money between them. One example by hand: A has 100, B has 0, transfer 30 from A to B. A ends at 70, B at 30, and A has 30 going out. That's my first transfer test.
The hard part isn't the arithmetic. It's the rules around moving money: not enough funds, sending to yourself, unknown accounts, and a transfer must never half-happen.
One question changes the design: will operations carry an ID that can be retried? If yes, I keep a set of applied IDs, so a retry is a no-op instead of a double charge.
Data: a map from account ID to an account with a balance in cents and a running outgoing total. I update that total on every transfer, because a later level will probably rank by it, and updating is cheaper than replaying history. I considered storing every transaction and deriving balances. That's the right model for a real ledger, but it's more code than this hour needs. I'll mention it at the end.
Order: create and deposit first, because everything uses them. Then transfer with its four failure cases, then ranking. Concurrency: one mutex on the whole bank. Per-account locks would need a fixed lock order to avoid deadlocks, and we don't need that throughput. Done is steps 1 to 3 tested, plus one integration test. Does that match what you'd expect?

Claude Code's gaps, and your answers

It suggests: negative amounts, int64 overflow, account IDs in different case, concurrent transfers, deposits to closed accounts.

Negative amounts: yes, that's money created from nothing. Adding it to step 1. Concurrency is already in my failure modes. Overflow: int64 cents goes past 92 quadrillion, so I'll skip it and say why. Case of IDs: the spec says IDs are strings, so exact match. Closed accounts aren't in this spec, so no.

Likely follow-up

Q: What if two transfers hit the same account at once? A: With the one mutex they run one after the other, so the balance check and the debit happen together. Without it, both could pass the check and overdraw. I'll add a test with goroutines and run the race detector.

B. A key-value store with expiry

"Build a key-value store with set, get and delete, and a time-to-live for each key."

In NOTES.md (you type)

# Problem
KV store; each key expires after its TTL.
e.g. set k ttl=1s at 10:00:00 → get at 10:00:00.5 = v; at 10:00:01 = gone

## Plan (each step starts with a failing test)
1. [ ] Set/Get/Delete → missing key, overwrite, delete missing = no-op
2. [ ] TTL → before expiry, exactly at expiry, overwrite resets TTL, ttl=0
3. [ ] Lock → 50 goroutines + go test -race
4. [ ] run() → integration

## Decisions
- expiry: lazy, on read (sweeper → Next)
- boundary: now ≥ expiresAt → expired
- clock: injected func() time.Time, no sleeps in tests

Say

It's a map where entries go stale. Example: set k with a one-second TTL at 10:00:00. At half a second I get it back. At exactly one second it's gone. That boundary is the interesting part, so I'm deciding it now: expired at exactly the deadline, and a test pins it.
Two designs for expiry: check on read, or a background sweeper. On read is simpler and always correct for get. The cost is memory held by keys that nobody reads again. I'll do on-read now and name the sweeper as the production step.
Time is the hard part to test, so I'll inject the clock: no sleeps in tests. Order: plain set, get and delete, then TTL, then the lock, then the integration test. Done is all four.
