The ledger on one card

The ledger guide is 14 sections. This is the part worth memorising, in plain words, in the order you will say it. It has the drawing, Ana's transfer told step by step on it, and the table schema. If you can say everything on this page without looking, you can pass the round.

Condensed 1 October 2026 from The ledger, end to end. Short on purpose: when something here feels thin, that is the section of the big guide to open.

1. The one sentence

A ledger is a notebook where every money movement is written as a pair of balancing lines, saved in one database commit. Only after that commit does the rest of the world get told about it.

What it must never do: move money twice for one intention, approve a debit from a balance it cannot verify, edit history, or say "done" before the commit.

The sentence that ties everything together

"Money becomes durable in the atomic store; events describe that fact afterwards. The idempotency key lives in the same commit as the money, so the same key always returns the same transaction."

3. Step 1: questions, numbers, rules

The question that decides everything

"Are we the ledger, a wallet on top of an existing ledger, or orchestration around payment rails?" Assume the authoritative ledger. Then: "Is a Processing state allowed?" Yes for money that leaves the bank; never for an internal transfer.

The features (what callers can do)

A client (the app, or a service like the dispute platform) submits a transfer with a key and gets a definite answer: done, rejected, or the same answer it already got. Anyone authorised reads a balance now, and a statement, including "as of" a past date. Other systems learn about every posting afterwards. A correction is a new posting linked to the old one, never an edit. Below the line: card authorisation, FX, the PIX rail itself, fraud, reporting.

The numbers (ask first, then do the maths)

2B transactions a month ≈ 770 / s average, ~8,000 / s peak (payday, Black Friday)
Each transfer = 2 entries + 2 aggregate updates + 1 outbox row ≈ 4–5 writes → ~30k writes / s peak
Entries 200 bytes × 4B / month ≈ 0.8 TB / month on the hot path
Balance reads ≈ transactions; feed reads 10× that, served from projections

The decision the numbers force

"Thirty thousand writes a second at peak is past one comfortable Postgres primary. So partitioning by customer is on the roadmap from day one, and cross-customer transfers become the explicit hard problem. If peak were under a few thousand writes a second I'd stay on one primary and measure."

The six rules (the qualities, as rules)

  1. Entries balance. Every transaction's entries sum to zero.
  2. Effectively once. Same key, same transaction, for a window that outlasts any retry.
  3. History is immutable. A mistake is a new, opposite entry that points at the wrong one.
  4. Never debit from stale funds. The funds check reads the authority, not a cache, not a replica.
  5. Authorise, post, clear and settle are different states. A hold lowers available, not posted.
  6. Every external movement is reconcilable against the counterparty's records.

The scope sentence, at minute twelve

"I'm designing the authoritative ledger: one strongly consistent decision per transfer, history that is never edited, everything else told afterwards. I'll design the single-shard version first and show where it splits. The two things I won't compromise: the funds check reads the authority, and the key lives in the same commit as the money."

4. Step 2: six nouns, three operations, the schema

AccountA bucket of value in one currency, with a version that goes up on every change.
TransactionThe business event: "Ana sent Bruno R$10", stamped with the client's key. Nubank calls it a movement.
EntryOne signed line against one account. Ana −10, Bruno +10. Never edited.
Account aggregateThe cheat sheet so you don't re-add years of entries: posted, held, available, version. Always rebuildable from the entries.
HoldA reservation (card authorisation) that lowers available without touching posted.
Outbox rowA note saying "publish this event later", written in the same commit.

Three operations. POST /transfers with the client's key, accounts, amount in minor units, currency, type. GET /accounts/{id}/balance, optionally as of a date. GET /accounts/{id}/entries for a period, from a projection. Holds and reversals are transfer types, not new endpoints. The caller comes from the token, never the body.

Why the client makes the key. Only the client knows a retry is a retry. If the ledger minted the key on arrival, a lost response plus a retry would move money twice. The app makes K1 once at the tap, saves it, and sends it on every retry. A service caller derives it from its own durable state, like case_id:PROVISIONAL_CREDIT:v1. Never uuid() per attempt.

The schema: the five rows written together

accounts          id, currency, posted, held, available, version
transactions      id (T1), caller, idempotency_key (K1), type, amount, currency, created_at
entries           id, transaction_id, account_id, amount (signed, minor units), created_at   -- append-only
idempotency_keys  (caller, key) → transaction_id, payload_hash, expires_at
outbox            id, transaction_id, event (json), published_at (null until Kafka acks)

Rules the schema enforces: SUM(entries.amount) per transaction = 0;  available = posted − held;
UPDATE accounts … WHERE id = ? AND version = ?   (zero rows updated means someone else got there first)

5. Step 3: the drawing

The version you name and don't draw: "One accounts table with a balance column: read it, subtract, write it back, publish an event from memory. It can double-spend, has no history, and loses the event if the process dies. So I won't draw it."

The version you draw. A transfer comes in. Four things happen in order:

  1. Look up the key. Not seen: continue. Seen with the same payload: return the stored transaction, touch nothing. Seen with a different payload: deterministic conflict, process neither.
  2. Validate. Both accounts exist, currency matches, Ana has the amount available, and her account version is the one just read.
  3. One commit writes the transaction, both entries, both aggregates with the version check, the key record, and the outbox row. All or nothing.
  4. Return "done", because the commit succeeded. Not because Kafka got anything.

After the commit, an outbox worker publishes the event to Kafka in order and marks the row after the ack. Consumers build the feed and statements, send notifications, feed fraud. They may see a message twice and dedupe.

The key on every arrow. App → ledger: the client's key K1. Ledger → Kafka: the transaction id. Shard → shard: K1:LEG_A, K1:LEG_B. Ledger → rail: a stable end-to-end id.

Stage 4: the clearing account · deep dive, about minute 30

Draw: Clearing account at the bottom left, with a dashed arrow from the partition.

Say it while you draw

"Only when Bruno lives on another shard. Leg A moves Ana's money into clearing in her partition's commit. Leg B moves it out to Bruno on his shard. Each leg has its own key, and I watch clearing by amount and age."

Stage 5: the external rail · when they ask about money that leaves the bank

Draw: External rail at the top right, with an arrow from the outbox worker.

Write on it: The key inside the box: "end-to-end id".

Say it while you draw

"Money that leaves the bank is Processing until the rail answers. The same end-to-end id goes on every retry, and reconciliation matches the rail's records."

Say its cost, then its gaps

"It costs four or five rows per transfer instead of one, a worker, and consumers that must dedupe. It doesn't yet handle: Kafka down for hours, read scale, a second primary, a hot account, and the failover window. Those are my deep dives; I'd go deepest on the cross-shard transfer and on failures."

The consistency line, said once: strong where I decide (the funds check, the commit, the aggregate); eventual where I only read (feed, statements, search); explicitly Processing where an external rail hasn't answered yet.

6. One transfer, end to end, on the diagram

Ana sends R$10 to Bruno, both Nubank customers. Follow the numbers.

  1. Ana taps "send". Her app creates key K1 once for this tap, saves it, and sends the transfer: source Ana, destination Bruno, 1000 (minor units), BRL, type internal transfer. If the network is slow and the app retries, it sends the same K1.
  2. The ledger looks up (caller, K1). Not seen, so it continues. Then it validates four things. Both accounts exist. Currency BRL. Ana's available balance covers 10 (posted minus holds). Ana's account version is 41, the number it just read. If Ana's card is being authorised at the same second, one of the two sees a stale version and re-validates. They never both win.
  3. One commit writes five rows. Transaction T1 with key K1. Entry Ana −10, entry Bruno +10, summing to zero. Ana's aggregate: posted and available down by 10, version 41 → 42, as a conditional update. Bruno's aggregate: up by 10, version 17 → 18. The key record K1 → T1 with the payload hash. One outbox row: "T1 posted". All or nothing. Saving the key and the money in separate steps is how a crash between them moves money twice.
  4. "Done" goes back to Ana, because the database committed. If the response is lost and the app retries K1, the ledger returns T1 again. Nothing else moves.
  5. The outbox worker reads unpublished rows in order, publishes T1's event, and marks the row only after Kafka acks. If the worker dies between publish and mark, it publishes again on restart. That is why consumers dedupe.
  6. Kafka carries the fact, partitioned by account key so Ana's events stay in order. It is not the truth. It is the truth being told. If Kafka is down for six hours, money is still right. The outbox backlog grows, and the alert is on the age of the oldest unpublished row.
  7. Projection builders consume T1: a feed item "sent R$10 to Bruno", a statement row for each, the search index. Every projection is rebuildable from the journal. If one drifts, replay it. Never touch an entry.
  8. Bruno's phone buzzes. A notification consumer sends "R$10 received". His feed shows it from the projection. His balance is one indexed read of the aggregate row: the authority, never the projection. That number is what the next debit will be authorised against.
  9. Reconciliation runs continuously. The sum of Ana's entries equals her aggregate. The journal sums to zero. External movements match the counterparty's records. A mismatch in a projection is a rebuild. A mismatch in an aggregate is an incident, because it authorises spending.
  10. If Bruno lived on another shard, you cannot update two databases in one commit. So the transfer becomes two legs joined by the clearing account. Leg A, in Ana's shard: Ana −10, clearing +10, key K1:LEG_A, and a transfer record saying "leg A done". Leg B, in Bruno's shard: clearing −10, Bruno +10, key K1:LEG_B. Between the legs the money is in clearing, fully accounted for, and Ana sees Processing. A crashed worker reads the transfer record to know which leg is still owed. Monitor clearing by amount and by the age of its oldest item.

The transfer in one breath

"Ana's app makes the key once. The ledger checks the key, validates available funds against the account version, and in one commit writes the transaction, two balancing entries, both aggregates, the key record and an outbox row. Done comes from the commit. A worker then tells Kafka, consumers build the feed and dedupe, and Bruno's balance is read from the aggregate, never the feed. If they're on different shards, two legs through clearing, each with its own key, Processing in between."

7. The three timeouts, and the one rule

  • Timeout before the commit. Nothing moved. A retry with K1 is just a first attempt.
  • Timeout after the commit. The retry with K1 returns the same T1. You never infer the outcome from a timeout, and you never send a fresh key.
  • Committed, but the event was lost. The outbox republishes. The event exists if and only if the money moved.

The one rule that protects everything

"If the ledger can't verify available funds, because a shard is down or a failover is in progress, it refuses the debit rather than approving from a cache or a replica. A few seconds of 'try again' beats a loss you can't recover."

8. When things break

For any failure, answer these six: What committed? What retries, with which key? What can duplicate? What does the customer see? Which metric alerts? What does an operator safely do?

FailureAnswer in one line
Two debits on Ana at onceBoth read version 41. One commits to 42. The other's conditional update matches zero rows, reloads, re-validates, and may now be declined. Never both.
Same key, different payloadDeterministic conflict. Process neither; the caller reused one identity for two intentions.
Kafka down for six hoursEvery posting still works. Outbox backlog grows; feeds and notifications go stale; it drains in order when Kafka returns. Alert on outbox age, not on Kafka health.
A projection driftsRebuild it from the journal alongside the old one, switch atomically. Never touch entries.
Someone says "rebuild balances from Kafka"No: that authorises debits from an eventually consistent source. Kafka distributes facts; it can't be the atomic boundary that ties the funds check, the entries and the key together.
Leg B can never completeMoney sits in clearing, visible by amount and age. Policy decides whether to reverse leg A with a new linked entry. Never delete leg A.
Single point of failure?The write authority's primary, one per partition. Synchronous replica in another zone, automated promotion in seconds; during it, new debits are rejected, reads keep working from projections. Failover time is my availability ceiling.

Degrades, never dies. Primary failing over: "try again in a moment" on a transfer, history still readable. Kafka down: transfers done but late in the list. Projection store down: "your history is delayed". External rail down: money in clearing, Processing. One partition down: only its customers wait, and transfers to them sit in clearing.

When they say "it's down, now what?"

"Money is real only when the posting commits in the atomic store, so I start every failure from that line. Two debits race: the version check lets one win, and the other re-validates and may be declined. Kafka is down: every transfer still posts, the list is late, and I alert on outbox age. The primary fails over: transfers get 'try again' for seconds, and history stays readable. A rail is down: the money waits in clearing, visible by amount and age. And nobody ever edits an entry."

Security in one breath. Only authenticated callers with a scoped command set: the dispute platform may issue a provisional credit, not an arbitrary transfer. Every posting records the caller and the business key. Nobody edits entries, engineers included. A correction is a new linked posting with an approval. Keys are scoped per caller so one can't replay another's.

9. Scale and performance

"Ten times the volume": the five-step answer

  1. Ask what grew. Transactions, accounts, entries per account, read traffic?
  2. Do the maths. Ten times is 80,000 transfers a second and 300,000 writes. That is many primaries, so partition by customer. Tag every transaction with the customer id from day one, so the split is possible.
  3. Scale what scales: outbox publishers, projection builders, reconciliation, every read that isn't the funds check.
  4. Say what doesn't: one write authority per account (that's the invariant, not an apology), hot accounts, and the failover time of the authority.
  5. Protect the rules while scaling. The three "improvements" that are bugs: cache the available balance, authorise from a read replica, and post asynchronously and confirm later for an internal transfer.

Hot account (a merchant settlement account, fee income, clearing). Scope it per day, per shard, per rail and roll up by projection. Or serialise on it with a per-account queue. Never a global lock, never a cached balance.

Say it once, in their own words

"Your own database makes this trade explicit: Datomic gives you immutability and free read scaling in exchange for serialised writes per database, which is exactly why you shard by customer, and exactly why cross-shard movement is the part I'd spend the most care on."

The follow-up questions, with short answers

A Lead candidate who failed in late 2025 reported mostly scale and performance questions. These are the ones to expect. Answer each with a number, then a decision.

They askAnswer in one line
"When would you partition?"When posting throughput or failover time crosses a threshold I set with load tests. Under a few thousand writes / s, one primary, and measure.
"Partition by what?"By customer, because customer-to-customer interaction is low, so most transfers stay on one shard. Tag every transaction with the customer id from day one.
"What would you measure?"Posting p99, version conflicts per account, oldest outbox row, replica lag, failover time, entries on the hottest account.
"One merchant account takes half the traffic."Scope it per day, per shard, per rail, and roll up by projection. Or serialise on it with a per-account queue. Never a global lock, never a cached balance.
"Reads are ten times the writes."The balance is one indexed read of the aggregate. Feed, statements, search and analytics come from projections on any store. Only the funds check reads the authority.
"The outbox falls behind."One publisher per partition, batch publishes, more Kafka partitions by account id. Dead-letter a poison row and keep publishing. Alert on the oldest row, not the count.
"Accounts with years of entries?"A checkpoint per account per period, so a rebuild replays from the last one. Archive cold entries to cheaper storage, still replayable.
"Reconciliation is too heavy."Run it on a replica or projection with a known lag, then confirm mismatches against the authority. A continuous per-account check, not one nightly pass.
"Cross-shard transfers are slow."Machines don't help: each is two legs through clearing. That's why I partition by customer. Watch the clearing balance and its oldest item.
"Balance as of three months ago?"Sum the entries up to that time, or replay from the nearest checkpoint. History is append-only, so it's a query, not a project.

"How would you improve performance?"

This question is about latency on the posting path, not about scale. That path holds five steps: key lookup, account reads, funds check, conditional update and one commit. Publication, projections and notifications already run after the commit. The target is tens of milliseconds at p99. If p99 is bad, look in this order:

  1. A hot account row: version conflicts and retries.
  2. A lock held across something slow, such as a network call inside the transaction.
  3. An unindexed key or account lookup.
  4. Only then, the database itself.

Say it

"The posting path is key lookup, account read, funds check, conditional update and one commit, and that's my tens-of-milliseconds p99. If it's slow, I look at a hot account row first, then a lock held across a slow call, then a missing index, and only then the database. The biggest win in most real ledgers is taking a synchronous call out of the transaction, not tuning the database."

10. Rollout, in three lines

One transfer type, one country. Shadow the old ledger: post to both, compare totals, nobody reads the new one. Then a small cohort behind a kill switch. Partition only when a measurement says so, never pre-emptively.

Schema changes after launch: add fields, never repurpose. Expand, migrate, contract. Events carry a schema version, and consumers accept N and N+1 during a rollout. Never rewrite entries. Caching: display balances and versioned reference data, under a version key, like their evergreen cache. Never the thing that decides, which is the available balance.

11. Lead signals, in their words

The Buenos Aires Lead posting names four things: trade-offs said out loud, failure-domain isolation, observability, and disaster recovery. Here is where each one lives in this design, and the sentence to say.

Communicating trade-offs

A trade-off has three parts: the choice, what it buys, and what it costs. Say all three, every time. Three choices carry this design.

  • The clearing account instead of two-phase commit. It buys transfers across shards with no locks held between databases, and an in-between state that anyone can see. It costs a Processing state and a clearing balance to watch.
  • A version check instead of a row lock. It buys no waiting and no deadlocks. It costs retries when one account is hot.
  • The outbox instead of publishing inside the request. It buys a "Sent" that never waits on Kafka. It costs a feed that can lag behind the money.

Say it

"Clearing instead of 2PC: I gain operability and lose the clean all-or-nothing. The customer sees Processing between the legs, and a stuck transfer is a visible row with an age, not an in-doubt lock."

Failure-domain isolation

A failure domain is the set of things that break together. A Lead keeps each domain small, so that a failure stays local and the rest of the bank keeps working.

  • A partition is a failure domain. Customers split by customer id. When one partition goes down, only its customers wait, and transfers to them sit in clearing.
  • The posting path is its own domain. Kafka, the projections and the feed sit after the commit. Their failure makes the list late, never a debit wrong.
  • Hot accounts get split. A merchant or clearing account is scoped per day, per shard and per rail, so one busy account can't slow every customer.

Say it

"A partition is my failure domain. If one goes down, only its customers wait. Transfers to them sit in clearing, visible by amount and age, and nothing else stops."

Observability

Measure the things that move money wrongly or late. Kafka's health on its own says little about the customer.

  • Six numbers to watch:
    • Posting p99.
    • Version conflicts per account.
    • The age of the oldest outbox row.
    • Replica lag.
    • The clearing balance, and the age of its oldest item.
    • Reconciliation mismatches.
  • One id across everything. The client's key and the transaction id travel into every entry, event and external call. So one id tells the whole story of one transfer.
  • One alert does most of the work. The age of the oldest outbox row catches Kafka down, a dead worker, a poison row and a partition with no consumer.

Say it

"I alert on the age of the oldest outbox row, not on Kafka health. That one number catches Kafka down, a crashed worker and a poison row. And clearing is watched like a customer account, by amount and by age."

Disaster recovery

Disaster recovery has two numbers. The recovery point is how much committed money you may lose. The recovery time is how long until the bank works again. State both for each disaster, and say who decides.

  • A zone dies. The synchronous replica in another zone takes over in seconds. Recovery point: zero. During the switch, new debits are rejected and reads keep working from projections.
  • A region dies. An asynchronous replica in a second region takes over, and a human decides when. Recovery point: the last few seconds of transfers. The books still balance, because a commit is lost whole, never half. Reconciliation against the event stream, the rails and the client's own record finds the lost transfers. They are re-posted once, under their original keys.
  • Bad code or bad data. Entries are never edited, so recovery is fix-forward with new linked postings. Projections rebuild from the journal. An account aggregate is rebuilt from its entries in an audited repair.
  • Restores are fast because of checkpoints. A rebuild replays each account from its last checkpoint, not from the first entry.

The region numbers are an assumption to say out loud. Synchronous replication across regions would make the recovery point zero, but every commit would pay a 50 to 150 ms hop. The posting budget is tens of milliseconds, so the trade is a few seconds of exposure that reconciliation repairs.

Say it

"Losing a zone costs seconds and no money. Losing a region is a human decision with a few seconds of exposure. The books still balance because commits are lost whole, and reconciliation with the rails and the clients re-posts what was lost, once, under the original keys."

12. Never say

  • "Kafka gives us exactly-once." (Your ledger makes the effect happen once; the network can't.)
  • "Roll back the transfer because the event didn't go out." (Committed money is a fact; the outbox republishes.)
  • "Rebuild the balance from Kafka." (That authorises debits from an eventually consistent source.)
  • "Cache the balance" or "authorise from a replica." (A stale balance is a double spend.)
  • "Use a float for the amount." (Integers in minor units; floats round, money doesn't.)
  • "It'll be a lot of data." (Say the number and what it decides: this one does outgrow one primary.)
  • "Edit the wrong entry." (A new, opposite entry that points at it.)
