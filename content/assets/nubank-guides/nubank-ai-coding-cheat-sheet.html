Own the plan: 10 parts, in order

  1. Restate — "The core of this is…"
  2. Example by hand — "X should give Y, because Z. That's my first test."
  3. Hard part — "The hard part isn't…, it's…"
  4. Design question — "One question changes the design: …? If yes A, if no B."
  5. Approach + rejected — "I'll use… because… I considered…, it costs…"
  6. Data — "A map keyed by… → O(1)."
  7. Order — "…first, because everything depends on it."
  8. Done — "Done is… tested. Stretch is…"
  9. Risks — CRELO, one line each
  10. Agree — "Does it match what you'd expect?"

On AI suggestions: accept / reject / park — always with "because". When it's right: "It's right, my plan missed X. Updating NOTES.md."

Failure modes — say before asked

Can Retries Ever Lose Orders?
  • CConcurrency — shared state? → mutex + go test -race. "The check and the write happen together." None shared? Say so.
  • RRetries — runs twice? → idempotent: key on ID, mark only after success. "Second run is a no-op, not a double charge."
  • EErrors — fail fast (money) or skip & report (reports). No panic. All-or-nothing: check everything, then write.
  • LLimits — what grows? → stream, evict, running totals. Name the limit.
  • OObserve — 1 structured log (what + where) + 1 metric to alert on.

Every diff: 6 checks

  1. Only what I asked?
  2. Errors returned + wrapped? No panic?
  3. Edge cases from NOTES.md?
  4. Clear names, one job per function?
  5. Can I explain every line?
  6. Simpler? → "Rejecting this because…"

Debug

Read the error aloud → hypothesis first → open the line → fix by hand if small → else E → re-run → name the root cause.

Never "it's broken, fix it". Never re-prompt 3× hoping.

Tests

  • TDD: test first → red (fails, so it tests something) → code → green.
  • Unit: one function alone. Many.
  • Integration: run() end to end, real text in, exact text out. 1–2. Checks the wiring.
  • Table-driven: {name, in, want} + t.Run loop. Names = behaviour.
  • One row each: empty · one · dup · exactly at limit · malformed · runs twice.
  • Expected values must be right, not copied from the code.
This case protects against… / The integration test protects the wiring.

Likely: bank in levels

L1 create/deposit/withdraw · L2 transfer, top-N spenders · L3 scheduled payments · L4 merge, balance at time

  • Fail: insufficient, same account, unknown, amount ≤ 0 — check all, then write
  • One mutex on the bank (per-account locks need a fixed order)
  • Retries: op ID set · ties: sort by ID
