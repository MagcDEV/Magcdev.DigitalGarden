1. Reading Go in 10 minutes

Go is small on purpose. There's no inheritance, no exceptions, no generics magic you'll need here. If you can read this block, you can read anything Claude Code produces in the session.

package main                    // every runnable program lives in package main

import (
    "errors"
    "fmt"
    "time"
)

// A struct is just a bag of named fields. Capitalized = exported (public).
type Transaction struct {
    ID        string
    Amount    int64       // cents, never float for money (see §4)
    Timestamp time.Time
}

// Functions return multiple values. The last is conventionally an error.
func parseAmount(s string) (int64, error) {
    if s == "" {
        return 0, errors.New("empty amount")   // errors are plain values
    }
    // ... real parsing here
    return 1234, nil                           // nil error = success
}

// A method: the thing before the name is the "receiver". *T = pointer, can mutate.
func (t *Transaction) Reverse() {
    t.Amount = -t.Amount
}

func main() {
    amount, err := parseAmount("12.34")   // := declares AND assigns. Type is inferred.
    if err != nil {                        // you check errors immediately, every time
        fmt.Println("bad input:", err)
        return
    }

    txs := []Transaction{}                 // a slice: a growable list
    txs = append(txs, Transaction{ID: "a", Amount: amount, Timestamp: time.Now()})

    seen := make(map[string]bool)          // a map: hash table. make() allocates it.
    for _, tx := range txs {               // range gives index, value. _ ignores one.
        if seen[tx.ID] {                   // missing key returns the zero value (false)
            continue
        }
        seen[tx.ID] = true
    }
    fmt.Printf("%d unique\n", len(seen))
}

The ten things to know

  • Zero values. Every type has a default: 0, "", false, nil. An unset struct field is the zero value, never "undefined". Senior Go leans on this.
  • := vs =. := declares a new variable. = assigns to an existing one. Mixing them up causes "shadowing" bugs (see §14).
  • Errors are values. No try/catch. A function returns (result, error) and you check if err != nil right there.
  • Pointers are simple. &x takes the address, *p reads through it. Use pointer receivers when a method mutates or the struct is big. Otherwise values are fine.
  • Interfaces are implicit. If your type has the methods, it satisfies the interface. No implements keyword. io.Reader is the one you'll meet most.
  • defer runs a call when the function returns. Used for Close() and Unlock(). Reads as "cleanup, guaranteed".
  • Slices are views over an array. append may or may not allocate. Treat the return value of append as the new slice, always.
  • Maps must be created with make (or a literal) before writing. Iteration order is random by design.
  • Capitalization is visibility. Parse is public, parse is private to the package. In a single-package interview this barely matters, but it signals intent.
  • gofmt is law. There is one formatting style. Run it and never argue about braces.

2. Project setup and commands

The environment is a browser VS Code with a terminal. The first thing you (or Claude Code) do:

go mod init interview          # creates go.mod; needed before `go test` works
go run .                       # build and run package main in this folder
go test ./...                  # run all tests
go test -run TestParse -v      # one test, verbose
go test -race ./...            # race detector: run this if you used goroutines or a mutex
go vet ./...                   # static checks, catches real bugs (unused results, printf mistakes)
gofmt -l .                     # lists files that aren't formatted; empty output = clean

File layout for a 60-minute problem

interview/
  go.mod
  main.go          // tiny: read input, call the core, print output, exit code
  model.go         // types: Transaction, Report, sentinel errors
  parse.go         // input -> []Transaction
  core.go          // the actual logic
  parse_test.go
  core_test.go
  NOTES.md         // your plan and edge cases, visible to the interviewer
Separating parse / core / main means the core logic takes plain Go values and is trivially testable. main stays under 30 lines. You can say "the core has no idea where the data came from" and mean it.

3. Errors: the senior way

This is the single area where non-experts and experienced Go engineers look most different. Get this right and the whole session reads as careful.

Rule 1: return errors, never panic on input

// Bad: crashes the program on bad data.
func mustParse(s string) int64 {
    n, err := strconv.ParseInt(s, 10, 64)
    if err != nil {
        panic(err)
    }
    return n
}

// Good: the caller decides what a failure means.
func parseInt(s string) (int64, error) {
    n, err := strconv.ParseInt(s, 10, 64)
    if err != nil {
        return 0, fmt.Errorf("parse %q as integer: %w", s, err)
    }
    return n, nil
}
panic is for programmer bugs, not for user input. In a payments context, a malformed line should be a visible, handled failure, not a crash. Say that.

Rule 2: wrap with %w and add context

Every time an error passes through a layer, add what that layer knows. %w keeps the original error inspectable.

func ParseFile(path string) ([]Transaction, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, fmt.Errorf("open %s: %w", path, err)
    }
    defer f.Close()

    txs, err := ParseTransactions(f)
    if err != nil {
        return nil, fmt.Errorf("parse %s: %w", path, err)
    }
    return txs, nil
}
// Result reads like a stack: "parse input.csv: line 12: malformed record: amount "12.3.4""

Rule 3: sentinel errors for cases the caller must distinguish

var (
    ErrMalformed = errors.New("malformed record")
    ErrDuplicate = errors.New("duplicate transaction")
)

// Producer wraps the sentinel:
return Transaction{}, fmt.Errorf("%w: empty id", ErrMalformed)

// Consumer checks identity through any number of wraps:
if errors.Is(err, ErrMalformed) {
    log.Printf("skipping bad line: %v", err)
    continue
}
Callers branching on errors.Is instead of string-matching error messages is a clear marker of someone who has maintained Go in production.

Rule 4: handle each error exactly once

Either log it, or return it, or both with a reason. Logging and then returning the same error at every layer produces duplicate noise in production logs. Pick one place, usually main.

func main() {
    if err := run(os.Args[1:], os.Stdin, os.Stdout); err != nil {
        fmt.Fprintln(os.Stderr, "error:", err)
        os.Exit(1)
    }
}
The run() pattern: main only translates an error into an exit code. Everything else is testable because it takes io.Reader/io.Writer, not files.

4. Modeling data (and money)

Money is an integer

// Never: float64 can't represent 0.1 exactly. 0.1 + 0.2 != 0.3.
type Transaction struct { Amount float64 }

// Always: smallest unit, as an integer. Name the unit.
type Transaction struct { AmountCents int64 }

// Parse "12.34" into 1234 without ever touching a float.
func parseCents(s string) (int64, error) {
    neg := strings.HasPrefix(s, "-")
    whole, frac, _ := strings.Cut(strings.TrimPrefix(s, "-"), ".")
    if whole == "" || !isDigits(whole) || !isDigits(frac) {   // "", ".5", "--5", "1.x"
        return 0, fmt.Errorf("amount %q is not a decimal number", s)
    }
    if len(frac) > 2 {
        return 0, fmt.Errorf("amount %q has more than 2 decimals", s)
    }
    for len(frac) < 2 {
        frac += "0"
    }
    n, err := strconv.ParseInt(whole+frac, 10, 64)
    if err != nil {
        return 0, fmt.Errorf("amount %q: %w", s, err)
    }
    if neg {
        n = -n
    }
    return n, nil
}

func isDigits(s string) bool {
    for _, r := range s {
        if r < '0' || r > '9' {
            return false
        }
    }
    return true
}
Check the empty string before parsing. Without the isDigits guard, "" pads to "00" and parses as 0 with no error, and "--5" comes back as +500. The table in §7 has a row for each.
Saying "I'm storing cents as int64 because floats lose precision and this is money" to a fintech interviewer is worth more than any algorithm. It's the first thing Andrey's team would check in a code review.

Named types for IDs and states

type AccountID string              // can't accidentally pass a TransactionID where an AccountID goes

type Status int                    // an "enum": a named int with constants
const (
    StatusPending Status = iota    // 0
    StatusPaid                     // 1
    StatusFailed                   // 2
)

func (s Status) String() string {
    switch s {
    case StatusPending: return "pending"
    case StatusPaid:    return "paid"
    case StatusFailed:  return "failed"
    }
    return fmt.Sprintf("Status(%d)", int(s))
}

Time

  • Use time.Time, not strings or ints, inside the program. Parse at the edge, once.
  • Compare with a.Before(b), a.After(b), a.Equal(b). Never == (it compares internal fields including location).
  • Differences are time.Duration: b.Sub(a) <= 5*time.Minute.
  • Parse with a layout: time.Parse(time.RFC3339, s). Be explicit about UTC in tests.

5. Slices and maps without surprises

// Nil map: reading is fine, writing panics.
var m map[string]int
m["a"] = 1                        // PANIC: assignment to entry in nil map
m = make(map[string]int)          // now it's safe

// Two-value lookup tells you "present?" separately from the value.
v, ok := m["a"]
if !ok { /* key absent */ }

// Map iteration order is random. If output order matters, sort the keys.
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)

// Sorting a slice of structs (Go 1.21+). Copy first if the caller's order matters.
sorted := slices.Clone(txs)
slices.SortFunc(sorted, func(a, b Transaction) int {
    return a.Timestamp.Compare(b.Timestamp)
})

// A "set" is a map to struct{} (zero bytes per value) or to bool (more readable).
seen := make(map[string]struct{})
seen[id] = struct{}{}
_, exists := seen[id]

// Preallocate when you know the size: avoids repeated growth.
out := make([]Transaction, 0, len(input))
A range loop copies each element. for _, tx := range txs { tx.Amount = 0 } changes nothing. Use the index: txs[i].Amount = 0, or a slice of pointers.

6. Parsing input safely

Three practice problems start with "parse this". The pattern is the same every time: take an io.Reader, stream it, validate each record, report line numbers in errors.

func ParseTransactions(r io.Reader) ([]Transaction, error) {
    cr := csv.NewReader(r)
    cr.FieldsPerRecord = 4          // csv package rejects rows with the wrong count for us

    var out []Transaction
    line := 0
    for {
        rec, err := cr.Read()
        if errors.Is(err, io.EOF) {
            break
        }
        line++
        if err != nil {
            return nil, fmt.Errorf("line %d: %w", line, err)
        }
        if line == 1 && rec[0] == "id" {
            continue                    // header
        }
        tx, err := parseRecord(rec)
        if err != nil {
            return nil, fmt.Errorf("line %d: %w", line, err)
        }
        out = append(out, tx)
    }
    return out, nil
}

func parseRecord(rec []string) (Transaction, error) {
    if rec[0] == "" {
        return Transaction{}, fmt.Errorf("%w: empty id", ErrMalformed)
    }
    cents, err := parseCents(rec[2])
    if err != nil {
        return Transaction{}, fmt.Errorf("%w: %v", ErrMalformed, err)
    }
    ts, err := time.Parse(time.RFC3339, rec[3])
    if err != nil {
        return Transaction{}, fmt.Errorf("%w: timestamp %q", ErrMalformed, rec[3])
    }
    return Transaction{ID: rec[0], AccountID: rec[1], AmountCents: cents, Timestamp: ts}, nil
}
io.Reader instead of a filename means the test passes strings.NewReader("id,acc,amount,ts\n...") and never touches disk. Line numbers in errors mean a support engineer can find the bad row at 3am. Both are things you can say out loud.

If the input could be huge, say so and switch to processing record by record instead of building a slice. Same loop shape, you just call the core per record. Don't do it unless asked; mention it.

7. Table-driven tests

This is the idiomatic Go test shape. Interviewers recognize it instantly. No assertion library needed.

Write it first. The panel names TDD: for each step, the test comes first and fails, then the code makes it pass. Say what each case protects against as you read it. Unit tests cover each function; one integration test through run() covers the wiring (§11 has one).

func TestParseCents(t *testing.T) {
    tests := []struct {
        name    string
        in      string
        want    int64
        wantErr bool
    }{
        {"whole", "12", 1200, false},
        {"two decimals", "12.34", 1234, false},
        {"one decimal", "12.3", 1230, false},
        {"negative", "-0.05", -5, false},
        {"zero", "0", 0, false},
        {"three decimals rejected", "1.234", 0, true},
        {"not a number", "abc", 0, true},
        {"empty", "", 0, true},
        {"no whole part", ".5", 0, true},
        {"double sign", "--5", 0, true},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            got, err := parseCents(tc.in)
            if (err != nil) != tc.wantErr {
                t.Fatalf("err = %v, wantErr %v", err, tc.wantErr)
            }
            if got != tc.want {
                t.Errorf("got %d, want %d", got, tc.want)
            }
        })
    }
}

Test habits that show care

  • Case names describe the behavior, not the input: "exactly at window boundary", not "case 3".
  • t.Fatalf when continuing makes no sense (nil result); t.Errorf when you want to see all failures in one run.
  • Test the error kind with errors.Is(err, ErrMalformed), not the message string.
  • One behavior per case. If a case has three asserts about unrelated things, split it.
  • Boundaries get their own case: window exactly equal, cap exactly reached, TTL exactly expired.
  • Fixed times in UTC: time.Date(2026, 1, 1, 10, 0, 0, 0, time.UTC). Never time.Now() in a test.
When Claude Code writes tests, read the expectations. It will sometimes write a test that asserts whatever the code currently does, bug included. Catching one of those out loud is a highlight moment.

8. Injecting time and I/O

The two things that make code untestable are time.Now() and the filesystem. Senior Go pushes both to the edge.

type Store struct {
    data map[string]entry
    now  func() time.Time       // injected clock; production uses time.Now
}

func NewStore() *Store {
    return &Store{data: make(map[string]entry), now: time.Now}
}

// In a test:
clock := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
s := NewStore()
s.now = func() time.Time { return clock }
// ... later:
clock = clock.Add(time.Second)     // "time passes", deterministically
A function-typed field is the lightest way to inject a clock in Go. No interface, no mocking library. Say "I'm injecting the clock so expiry tests are deterministic" and move on. It's a one-liner that signals years of experience.

Same idea for I/O: core functions take io.Reader and io.Writer. Only main knows about os.Stdin, files, or os.Stdout.

9. Just enough concurrency

You probably won't need goroutines in 60 minutes. You might need a mutex if the store or rate limiter is "safe for concurrent use". Know this shape and nothing more.

type Store struct {
    mu   sync.Mutex             // protects data. Say that. Put it right above what it guards.
    data map[string]entry
}

func (s *Store) Set(key, value string) {
    s.mu.Lock()
    defer s.mu.Unlock()         // defer = unlocked on every return path, including early ones
    s.data[key] = entry{value: value}
}
  • Lock, defer Unlock, do the work. Never return between Lock and Unlock without defer.
  • Keep the critical section small. Don't do I/O or parsing while holding the lock.
  • sync.RWMutex if reads vastly outnumber writes. Mention it, don't reach for it by default.
  • If you used a mutex, run go test -race ./... on camera. That's the move.
  • If asked about scaling: "I'd shard the map by key hash to reduce lock contention" is a complete, honest answer.

If the problem does involve concurrent work, the one more thing to know is context.Context as the first parameter of anything that could be cancelled: func Process(ctx context.Context, ...), and if err := ctx.Err(); err != nil { return err } inside long loops.

10. Reliability patterns

This is Andrey's world. You don't need to implement all of these; you need to name the one that applies and implement it if cheap.

Idempotency: "safe to run twice"

// Processing is idempotent if re-running with the same input changes nothing.
type Processor struct {
    processed map[string]struct{}      // IDs already applied; in prod this is a DB table or a Kafka offset
}

func (p *Processor) Apply(tx Transaction) error {
    if _, done := p.processed[tx.ID]; done {
        return nil                  // already applied; not an error, just a no-op
    }
    if err := p.apply(tx); err != nil {
        return fmt.Errorf("apply %s: %w", tx.ID, err)
    }
    p.processed[tx.ID] = struct{}{}   // mark only after success
    return nil
}
If this job gets retried, we'll see the same transactions again. I'm keying on the transaction ID so a second run is a no-op rather than a double charge.

Fail fast vs skip and continue

Decide explicitly, say why, and make it a parameter if it's cheap:

  • Fail fast (return on first bad record): when partial results are dangerous. Money movement, ledgers.
  • Skip and report (collect bad lines, continue): when one bad row shouldn't block a thousand good ones. Reports, analytics.
type ParseResult struct {
    Transactions []Transaction
    Rejected     []RejectedLine     // line number + reason; never silently dropped
}

Atomic output

If you write a file, write to a temp file and rename. A crash mid-write leaves the old file intact, never a half-written one.

tmp, err := os.CreateTemp(filepath.Dir(path), "report-*.tmp")
// ... write to tmp, tmp.Close()
if err := os.Rename(tmp.Name(), path); err != nil { /* ... */ }

You won't implement this in the session. You'll mention it in the final walkthrough.

Validate at the boundary, trust inside

Parse and validate once at the edge, produce a well-typed Transaction, and let the core assume it's valid. Don't re-check "is amount parseable" in five places.

Observability in one line

You won't build logging. But in the walkthrough: "I'd log at the parser with line number and reason, and emit a counter for rejected records, because that's what you'd alert on."

11. Worked example: duplicate detection

Practice problem 1, the core. Read it until every line is obvious. This is roughly what a good 25-minute build looks like.

// core.go
package main

import (
    "slices"
    "time"
)

type Report struct {
    Unique     []Transaction
    Duplicates []Transaction
}

// FindDuplicates flags a transaction as a duplicate when the same account
// has a transaction with the same amount within `window` of an earlier one.
// The input slice is not modified.
func FindDuplicates(txs []Transaction, window time.Duration) Report {
    sorted := slices.Clone(txs)
    slices.SortFunc(sorted, func(a, b Transaction) int {
        return a.Timestamp.Compare(b.Timestamp)
    })

    type key struct {
        account string
        cents   int64
    }
    lastSeen := make(map[key]time.Time)

    var rep Report
    for _, tx := range sorted {
        k := key{tx.AccountID, tx.AmountCents}
        if prev, ok := lastSeen[k]; ok && tx.Timestamp.Sub(prev) <= window {
            rep.Duplicates = append(rep.Duplicates, tx)
            continue
        }
        lastSeen[k] = tx.Timestamp
        rep.Unique = append(rep.Unique, tx)
    }
    return rep
}

Things to narrate while this comes together:

  • "Sorting a clone so the caller's slice isn't reordered under them."
  • "The key is account plus amount; a struct key in a map is fine and clearer than string concatenation."
  • "<= on the window: a transaction exactly at the boundary counts as a duplicate. I'll write a test for that boundary either way."
  • "I'm comparing against the last unique one, not the last seen. Otherwise a long chain of duplicates would all pass." Then point at the continue.
// core_test.go
func TestFindDuplicates(t *testing.T) {
    base := time.Date(2026, 1, 1, 10, 0, 0, 0, time.UTC)
    tx := func(id string, cents int64, offset time.Duration) Transaction {
        return Transaction{ID: id, AccountID: "acc-1", AmountCents: cents, Timestamp: base.Add(offset)}
    }

    tests := []struct {
        name    string
        in      []Transaction
        window  time.Duration
        wantDup int
    }{
        {"empty input", nil, time.Minute, 0},
        {"single", []Transaction{tx("a", 100, 0)}, time.Minute, 0},
        {"inside window", []Transaction{tx("a", 100, 0), tx("b", 100, 30*time.Second)}, time.Minute, 1},
        {"outside window", []Transaction{tx("a", 100, 0), tx("b", 100, 2*time.Minute)}, time.Minute, 0},
        {"exactly at boundary", []Transaction{tx("a", 100, 0), tx("b", 100, time.Minute)}, time.Minute, 1},
        {"different amount", []Transaction{tx("a", 100, 0), tx("b", 101, 10*time.Second)}, time.Minute, 0},
        {"out of order input", []Transaction{tx("b", 100, 30*time.Second), tx("a", 100, 0)}, time.Minute, 1},
        {"chain of three", []Transaction{tx("a", 100, 0), tx("b", 100, 40*time.Second), tx("c", 100, 80*time.Second)}, time.Minute, 1},
    }
    for _, tc := range tests {
        t.Run(tc.name, func(t *testing.T) {
            got := FindDuplicates(tc.in, tc.window)
            if len(got.Duplicates) != tc.wantDup {
                t.Fatalf("got %d duplicates, want %d", len(got.Duplicates), tc.wantDup)
            }
            if len(got.Unique)+len(got.Duplicates) != len(tc.in) {
                t.Errorf("lost transactions: %d in, %d out", len(tc.in), len(got.Unique)+len(got.Duplicates))
            }
        })
    }
}

Look at the "chain of three" case. With a 1-minute window, b (at 40s) is a duplicate of a. Is c (at 80s) a duplicate? It's 80s after a, the last unique, so no. That's a design decision the test pins down. Either answer is defensible; the senior move is that you decided and wrote the test.

The entry point and one integration test

The panel asks for at least one integration test, brought up without a prompt. The run() pattern from §3 makes it cheap: main only turns an error into an exit code, so the test calls run with a string for input and a buffer for output.

// main.go
package main

import (
    "flag"
    "fmt"
    "io"
    "os"
    "time"
)

func main() {
    if err := run(os.Args[1:], os.Stdin, os.Stdout); err != nil {
        fmt.Fprintln(os.Stderr, "error:", err)
        os.Exit(1)
    }
}

// run is the whole program minus the process: args, input and output come in
// as values, so the integration test can call it directly.
func run(args []string, in io.Reader, out io.Writer) error {
    fs := flag.NewFlagSet("dedupe", flag.ContinueOnError)
    window := fs.Duration("window", time.Minute, "duplicate window")
    if err := fs.Parse(args); err != nil {
        return err
    }
    txs, err := ParseTransactions(in)
    if err != nil {
        return fmt.Errorf("read transactions: %w", err)
    }
    rep := FindDuplicates(txs, *window)
    _, err = fmt.Fprintf(out, "unique: %d\nduplicates: %d\n", len(rep.Unique), len(rep.Duplicates))
    return err
}
// main_test.go
package main

import (
    "bytes"
    "errors"
    "strings"
    "testing"
)

// Protects the wiring: parse, core and output agree on the format.
func TestRunEndToEnd(t *testing.T) {
    in := strings.NewReader(`id,account,amount,ts
a,acc-1,10.00,2026-01-01T10:00:00Z
b,acc-1,10.00,2026-01-01T10:00:30Z
c,acc-2,5.50,2026-01-01T10:01:00Z
`)
    var out bytes.Buffer
    if err := run([]string{"-window", "1m"}, in, &out); err != nil {
        t.Fatalf("run: %v", err)
    }
    want := "unique: 2\nduplicates: 1\n"
    if got := out.String(); got != want {
        t.Errorf("output:\n%s\nwant:\n%s", got, want)
    }
}

// Protects against a bad line being dropped silently or crashing the run.
func TestRunMalformedLine(t *testing.T) {
    in := strings.NewReader(`id,account,amount,ts
a,acc-1,10.00,2026-01-01T10:00:00Z
b,acc-1,ten,2026-01-01T10:00:30Z
`)
    var out bytes.Buffer
    err := run(nil, in, &out)
    if !errors.Is(err, ErrMalformed) {
        t.Fatalf("err = %v, want ErrMalformed", err)
    }
    if !strings.Contains(err.Error(), "line 3") {
        t.Errorf("error %q does not name line 3", err)
    }
    if out.Len() != 0 {
        t.Errorf("wrote partial output: %q", out.String())
    }
}
The unit tests pin each piece. This integration test protects the wiring: the parser, the core and the output agree on the format. The second case checks that a bad line fails loudly with its line number and writes no partial report.
Two integration cases, the happy path and one failure, are enough. They run in milliseconds because nothing touches disk, and they would catch a refactor that breaks the format between layers.

12. Worked example: TTL key-value store

type entry struct {
    value     string
    expiresAt time.Time
}

type Store struct {
    mu   sync.Mutex
    data map[string]entry
    now  func() time.Time
}

func NewStore() *Store {
    return &Store{data: make(map[string]entry), now: time.Now}
}

func (s *Store) Set(key, value string, ttl time.Duration) {
    s.mu.Lock()
    defer s.mu.Unlock()
    s.data[key] = entry{value: value, expiresAt: s.now().Add(ttl)}
}

// Get returns the value and true if present and not expired.
// Expired entries are removed lazily on read.
func (s *Store) Get(key string) (string, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    e, ok := s.data[key]
    if !ok {
        return "", false
    }
    if !s.now().Before(e.expiresAt) {      // now >= expiresAt: expired, boundary inclusive
        delete(s.data, key)
        return "", false
    }
    return e.value, true
}

func (s *Store) Delete(key string) {
    s.mu.Lock()
    defer s.mu.Unlock()
    delete(s.data, key)                   // deleting a missing key is a no-op in Go. Idempotent for free.
}
func TestStoreExpiry(t *testing.T) {
    clock := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
    s := NewStore()
    s.now = func() time.Time { return clock }

    s.Set("k", "v", time.Second)
    if v, ok := s.Get("k"); !ok || v != "v" {
        t.Fatalf("before expiry: got (%q, %v), want (\"v\", true)", v, ok)
    }

    clock = clock.Add(time.Second)         // exactly at the boundary
    if _, ok := s.Get("k"); ok {
        t.Fatal("at boundary: expected expired")
    }
}

func TestStoreOverwriteResetsTTL(t *testing.T) {
    clock := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
    s := NewStore()
    s.now = func() time.Time { return clock }

    s.Set("k", "v1", time.Second)
    clock = clock.Add(500 * time.Millisecond)
    s.Set("k", "v2", time.Second)         // new TTL from now
    clock = clock.Add(800 * time.Millisecond) // 1.3s after first set, 0.8s after second
    if v, ok := s.Get("k"); !ok || v != "v2" {
        t.Fatalf("got (%q, %v), want (\"v2\", true)", v, ok)
    }
}

Talking points: lazy expiry vs a background sweeper (lazy is simpler, memory grows until read; say you'd add a sweeper goroutine with a ticker for production). Boundary inclusive or exclusive (you picked inclusive; the test enforces it). Zero TTL means "expires immediately", say whether that's intended.

13. Sketch: token bucket

type Bucket struct {
    mu        sync.Mutex
    capacity  float64
    tokens    float64
    perSecond float64
    last      time.Time
    now       func() time.Time
}

func NewBucket(capacity, perSecond float64) *Bucket {
    return &Bucket{capacity: capacity, tokens: capacity, perSecond: perSecond, last: time.Now(), now: time.Now}
}

func (b *Bucket) Allow() bool {
    b.mu.Lock()
    defer b.mu.Unlock()
    t := b.now()
    elapsed := t.Sub(b.last).Seconds()
    if elapsed < 0 {
        elapsed = 0                     // clock moved backwards (or a test swapped it): never take tokens away
    }
    b.tokens = math.Min(b.capacity, b.tokens+elapsed*b.perSecond)
    b.last = t
    if b.tokens >= 1 {
        b.tokens--
        return true
    }
    return false
}

Float is fine here: tokens aren't money, and fractional refill is the point. Say that, because you just told them floats are bad for money and they'll notice the switch. Tests: burst of capacity calls all allowed, the next denied, advance the clock, one more allowed.

NewBucket sets last from the real clock. A test that then swaps in a fixed past date sees a negative elapsed on the first call. Without the clamp, that drains the bucket and the burst test fails on call one. The clamp also covers a wall clock that steps backwards in production.

15. Phrases that signal seniority

Each of these is true, specific, and takes five seconds. Use the ones that apply; don't recite the list.

  • "Money as int64 cents, not float, because floats can't represent decimal fractions exactly."
  • "I'm wrapping with %w so the caller can errors.Is on it without parsing the message."
  • "Panic is for programmer bugs. Bad input is expected, so it's an error."
  • "The core takes an io.Reader so tests use a string and never touch disk."
  • "Injecting the clock so the expiry test is deterministic."
  • "Table-driven tests, one behavior per case, boundaries get their own row."
  • "Test first: here's the failing test for this step, now I'll ask for the code that makes it pass."
  • "This case protects against a retried transaction being counted twice."
  • "One integration test through run(), because no unit test checks that the layers agree on the format."
