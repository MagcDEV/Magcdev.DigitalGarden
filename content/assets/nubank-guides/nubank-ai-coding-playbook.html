1. The four things being scored

Straight from their guide. Every move in this playbook maps to one of these.

CriterionWhat it looks like on camera
Logical reasoning & decompositionYou break a vague ask into 3–5 testable steps before any code exists.
AI steering & collaborationPrecise briefs, small slices, you read everything, you redirect when it drifts.
Code readability & maintainabilitySmall focused functions, clear names, edge cases handled, tests that matter.
CommunicationYou narrate trade-offs and assumptions out loud, before generating, and you ask instead of guessing.

Their own words on what fails: going quiet, accepting code you didn't read, skipping tests, getting stuck without asking for a hint.

2. Before the call

  • Language decided and fixed: Go (swap if you change your mind, but decide before the call, never during).
  • Browser: Chrome, fresh profile or clean window, no extensions fighting the VS Code tab. Second monitor or split screen so Meet and the editor are both visible.
  • Audio tested. Headphones. Water next to you.
  • A notepad (paper or a scratch NOTES.md in the workspace) for the plan and the edge-case list. You will refer back to it.
  • This playbook open on your phone, not on the shared screen.
  • Read sections 3, 5 and 8 once more, 20 minutes before.

3. The opening (first 2 minutes)

When the editor loads, don't touch it. Orient the room first.

Before I start, I'll take a couple of minutes to make sure I understand the problem, write a short plan, and list edge cases. Then I'll build it in small slices with Claude Code, reviewing each one. I'll think out loud the whole time, so stop me whenever you want.

This one sentence tells Andrey you know how the round is scored. It also buys you the silence you need to read the problem.

Then, while reading the statement, narrate what you notice:

Inputs are X, output is Y. The ambiguous part is Z, I'll ask about that. The thing that could bite us is W.

4. The 60-minute timeline

Times are targets, not rules. The point is that each phase has a visible exit, and you announce it.

  1. 0–10

    Understand and plan. No code.

    Scores: decomposition, communication
    • Restate the problem in one sentence. Get a nod.
    • Ask 3–4 clarifying questions (see bank in §6). Input size, format guarantees, what to do on bad input, what "done" means.
    • Write the plan in NOTES.md on screen: 3–5 steps, each with a verifiable result.
    • List edge cases under the plan: empty input, duplicates, malformed lines, boundaries, concurrency if relevant, "what if it runs twice".
    • State your data model and the main trade-off you're taking.
    Plan is set. Step 1 is the parser with a test, step 2 the core logic, step 3 the output. I'll tackle them in that order and we'll have something runnable after step 1.
  2. 10–15

    Brief Claude Code. Skeleton only.

    Scores: AI steering
    • Send the kickoff prompt (§5, template A). Language, structure, constraints, and "plan first, wait for my go".
    • Read its proposed plan out loud. Accept, trim, or correct it. Then say "go".
    • Skeleton lands: files, types, function signatures, a failing test. Run it.
  3. 15–40

    Build in slices. One step per prompt.

    Scores: AI steering, readability, communication
    • For each plan step: prompt (template B), read the diff aloud, run, accept or correct, tick the step in NOTES.md.
    • Keep each slice under ~50 lines of change. If it comes back bigger, say so and split it.
    • Explain at least one design choice per slice: why this structure, why this error handling.
    • Check in with Andrey at each tick: "Step 2 done, parser handles empty and malformed lines. Moving to the core."
  4. 40–52

    Tests on the hard cases.

    Scores: readability, decomposition
    • Go back to your edge-case list. Prompt for tests on those specifically (template D).
    • Read each test. Delete or fix any that only test the happy path or that assert the wrong thing. Say why.
    • Run them. A failing test here is good: it's your debug protocol on display (§8).
  5. 52–60

    Final pass and handoff.

    Scores: communication, readability
    • Walk the solution top to bottom as if handing it to a teammate: entry point, data flow, where errors surface.
    • Name what's fragile and what you'd do with another hour.
    • Ask your questions for Andrey (§10) if there's time.
    If this were going to production I'd add structured logging around the parser and make the writer idempotent. For the scope here, it's complete and the tricky cases are covered by tests.

5. Prompt templates

Claude Code reads plain technical language. Brief it like a strong teammate who has never seen the task: context, constraints, expected behavior, stop condition. Fill the yellow parts live.

A. Kickoff (once, after your plan is written)

We're solving this in Go. Problem: one-sentence restatement.

Constraints:
- Standard library only, no external deps.
- Package main, one file per concern: parser.go, core.go, main.go, plus _test.go files.
- Small functions, explicit error returns, no panics on bad input.

My plan is in NOTES.md. Before writing any code, tell me in 3-5 bullets how you'd structure it and which types you'd define. Then wait for my go.

B. One slice (repeat per plan step)

Step N: what this step does.

Expected behavior: input -> output, including the edge case for this step.
Keep it to the one function/file. Don't touch other files.
Don't write tests yet unless I ask. Show me the diff and stop.

C. Correction (when the output isn't what you want)

Not quite. What's wrong, in one line. Change only the specific thing: what it should do instead. Leave the rest as is.

D. Tests on hard cases

Write table-driven tests for function covering exactly these cases:
- empty input
- duplicate / boundary / malformed case
- the "runs twice" case
One assertion per case, clear case names. No happy-path-only tests.

E. Debug (only after you've stated your own hypothesis)

Test name fails with actual vs expected. I think the cause is your hypothesis. Confirm or correct that, and fix only that. Don't rewrite the function.

F. Final review

Review the full solution for: unhandled errors, naming, functions doing more than one thing, missing edge cases from NOTES.md. List findings, don't change anything yet.

Prompt rules of thumb

  • One task per prompt. If you wrote "and" twice, split it.
  • Always say what not to touch. It keeps diffs small and reviewable.
  • "Show the diff and stop" / "wait for my go" is how you stay in control.
  • If it starts running away (editing many files, adding deps), interrupt it and redirect. Interrupting is a positive signal.
  • If it produced something you don't understand, ask it to explain the lines before you accept. That's reviewing, not weakness.

6. Narration bank

Silence reads as uncertainty. Use these to keep talking, especially during the boring parts.

Clarifying questions (pick 3–4)

  • How large is the input: fits in memory, or should I stream it?
  • Can I trust the format, or should I expect malformed records? Skip them or fail fast?
  • Is the order of the output significant?
  • Can the same record appear twice? How should I treat that?
  • Is this run once, or repeatedly on the same data? (Idempotency.)
  • What does "done" look like for this hour: working CLI, a library with tests, or both?

While Claude Code works

While it generates, I'm expecting a struct for the record and a parse function returning an error. If it adds anything beyond that, I'll trim it.
This looks right. One thing I'd change: the name. I'll ask for that in the next prompt rather than nitpick now.
Rejecting this part: it swallows the error. I want it returned so the caller decides.

Trade-offs

I'm going with a map keyed by ID for O(1) lookup. Memory is fine at this size; if we were streaming millions I'd rethink.
I'm choosing to fail fast on a malformed line instead of skipping, because silent data loss is worse than a visible failure in a payments context. Happy to flip that if the requirement is different.

Checkpoints

Step 2 done and runnable. Next is the aggregation. Any concerns before I go on?
I'm about 25 minutes in and on plan. I'll leave the last 15 for tests and a final walkthrough.

7. Reviewing AI output

Do this on every diff, out loud, in roughly this order. Thirty seconds is enough.

  1. Does it do only what I asked? Extra files, extra features, extra deps: cut them.
  2. Errors: are they returned, not swallowed or panicked? Are they wrapped with context?
  3. Edge cases from NOTES.md: empty, nil, zero, duplicate, boundary. Is each one handled or deliberately deferred?
  4. Names and shape: would a teammate understand this function from its name and signature alone? Is it doing more than one thing?
  5. Can I explain every line? If not, ask Claude Code to explain it before accepting.
Scrolling past a diff and saying "looks good". The tips sheet calls this out by name. One rejected line per session is worth more than ten accepted ones.

8. Debug protocol

A failing test or runtime error is the best moment in the hour. It's where "owning the bugs" is observed. Follow this order, and narrate each step.

  1. Read the error fully, aloud. Line number, message, actual vs expected.
  2. State a hypothesis before touching anything. "I think this is the boundary check in the loop."
  3. Verify it yourself: open the file, point at the line, add a print or a focused test if needed.
  4. Fix it by hand if it's small. One-line fixes typed by you look better than a re-prompt.
  5. Otherwise prompt with the hypothesis (template E). Never "it's broken, fix it".
  6. Re-run, confirm, say what the root cause was.
Re-prompting three times with slightly different wording and hoping. That's the exact behavior the guide says is penalized.

9. When things go wrong

I'm stuck and the clock is moving

Ask for a hint. Their guide says it's normal and expected. Phrase it as a decision, not a plea:

I see two ways to handle this and I'm not sure which matches what you'd expect. Would you lean toward A or B?
Claude Code went off the rails (rewrote everything, added a framework)

Interrupt it. Say what happened and why you're rejecting it:

That's more than I asked for. I'm discarding this and re-briefing with a tighter scope.

Then template C with explicit "don't touch" boundaries. Mention that this is why you work in slices.

Running out of time with steps left

Announce a scope cut at the 45-minute mark, not at 58. Prioritize a working, tested core over a complete but shaky whole.

I'm going to drop step 4 and make sure steps 1–3 are solid and tested. I'll describe how step 4 would slot in during the walkthrough.
The environment is slow or Claude Code is unresponsive

Say it, don't suffer silently. Keep narrating what you'd be doing. Write the next function signature by hand while you wait. Interviewers are used to this and will not hold it against you.

Andrey pushes back on a choice

Engage, don't fold or dig in. Ask what he's optimizing for, then either adjust or defend with a reason:

Good point. If we expect retries, you're right that this needs to be idempotent. Let me add a check on the ID before writing.
I don't understand the problem statement

Ask. Then restate it until you get a yes. Guessing quietly is the riskier move by far, and they say so.

10. About Andrey

Staff engineer, six and a half years at Nubank, all on the Colombia launch: first Bills & Payments, now cross-BU stability and reliability. Clojure, Datomic, Kafka background.

What that changes for you: the problem will be the standard one, but his follow-ups will come from reliability instincts. Pre-empt them during planning and you'll sound like a colleague:

  • "What happens if this runs twice?" Mention idempotency early.
  • "What if a record is malformed?" Decide fail-fast vs skip, say why.
  • "What if it's partially processed and crashes?" Note where you'd add a checkpoint or make writes atomic.
  • "How would you know it's broken in production?" One line about logging or a metric.

Don't use Clojure. He'll know you picked your language and won't expect his.

Questions to ask him

  • How does the Colombia BU handle reliability incidents that cross squad boundaries?
  • How are teams at Nu using AI coding tools day to day, and what has changed in code review because of it?
  • What distinguishes a strong session in this round from an average one, in your experience running it?

11. Practice plan

Four timed mocks, each 60 minutes, each narrated aloud as if someone is listening. Record audio for at least two of them and listen for the silences.

  1. Transaction CSV reconciliation. Parse records, detect duplicates within a time window, output a summary. Edge cases: malformed lines, out-of-order timestamps, same ID different amount.
  2. In-memory key-value store with TTL. Get/set/delete, expiry, simple eviction. Edge cases: zero TTL, overwrite with new TTL, expiry at exact boundary.
  3. Bill payment scheduler. Payments with due dates and a daily cap: decide what runs today. Must be safe to run twice. Edge cases: cap exactly reached, past-due items, empty day.
  4. Token-bucket rate limiter. Allow/deny with refill. Edge cases: burst at start, refill boundary, zero capacity.

After each mock, grade yourself 1–4 on the four criteria in §1 and write one sentence on what to change next time. By mock three the opening script and the slice rhythm should feel automatic.
